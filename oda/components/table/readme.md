# `oda-table`

## 1. Что это

Новая таблица — переписывание `oda-table` рядом (фаза 01). Та же задача (табличное представление массивов по описаниям колонок), но на явной модели «данные → слои → представление» вместо лапши. Старая таблица не трогается, пока новая не закроет её чек-лист.

## 2. Зачем это нужно

`oda-table` обросла пятью ответственностями в одном файле, мутациями данных потребителя, неявными контрактами и точечными заплатками. Чинить дальше — дороже, чем построить рядом чисто. Этот компонент — чистое место: каждый этап виден и тыкается руками.

## 3. Как это работает

Слои данных: входные `dataSet` → обёрнутые (view-модель строки) → фильтрованные → отсортированные → линеаризованные → сгруппированные → окно. Таблица — представление текущего слоя; сброс нижележащих слоёв при изменении вышележащего делает Reactor (`collect_deps`/`reset_deps`). Состояние строк (раскрытие, отметка, текущая) — на обёртках строк, состояние колонок (ширины, раскрытие, скрытие, порядок, сортировка, группировка, фильтры) — в сохраняемых свойствах самой таблицы. Ни то, ни другое не пишется в данные и в метаданные.

**ViewRow — строка слоя:** `{data, level, expanded, checked, focused, allowExpand, hasChildren, items}`. `data` — тот же объект потребителя (не копия, таблица его не меняет), `level` — уровень дерева (0 у корня). Два разных признака о детях: **`allowExpand`** — «дети могут быть» (заглядывание в данные на шаг, без сборки обёрток; им решается, показывать ли экспандер) и **`hasChildren`** — «дети фактически загружены» (кэш `__items` уже есть; по ним фильтр может идти, не провоцируя загрузку — важно для асинхронных детей). `expanded`/`checked`/`focused` — **состояние представления на самой обёртке** (обёртка одна на объект данных, переживает пересчёт и реактивна), поэтому `row.expanded = true` из строки пересобирает слои без ручных инвалидаций.

**Дети собираются лениво.** `wrapTree` строит только переданный уровень; `items` у обёртки — ленивый кэш (`__items`): потомки оборачиваются при первом обращении, а линеаризация читает `items` только у раскрытых узлов. Свёрнутые ветви не обходятся вовсе, а уже построенные дети переживают сворачивание — повторное раскрытие берёт готовые. Поэтому стоимость сборки — от раскрытого, а не от всего дерева (для будущего асинхронного получения детей это ещё и обязательное условие).

**Сортировка — ленивая.** `flattenTree` сортирует братьев на **посещаемых** уровнях: свёрнутые ветви не обходятся, значит их дети не сортируются и не собираются; сортировка раскрытого происходит при очередной линеаризации.

**Фильтр — только при значении, и раскрывает виртуально.** Нет `filter` — `filterTree` не вызывается вовсе. Есть — при `filterForceExpanding` (по умолчанию `true`) дерево раскрывается на полную глубину для поиска и фильтруется целиком: раскрытие идёт через `open` в линеаризации, а `expanded` в обёртках **не меняется**, поэтому снятие фильтра возвращает прежнее состояние само. На время активного фильтра экспандер выключен (`expander-disabled`), чтобы не конфликтовать с виртуальным раскрытием. `filterForceExpanding: false` переводит фильтр в `deep: false` — спуск только в узлы с уже загруженными детьми (`hasChildren`), новые обёртки не собираются: предохранитель для асинхронных детей (рекурсивный обход незагруженных узлов недопустим). Проверено зондом: `force=false`, фильтр «этап» — 12 строк, **0** новых обёрток.

**Колонки — дерево полей WORK.** Вход — `metadata` (корневые поля: `id`, `label`, `type`, `fields`, `control`, `readonly`); ключи детей и значения настраиваются (`childrenKey`, `valueKey`). `wrapColumns` строит обёртки `ViewColumn`: `field` — read-only ссылка на поле, `key`/`label`/`level`/`parentKey`, ленивые `children` из `childrenKey`, `allowExpand` («дети могут быть») vs `hasChildren` («собраны»). Обёртка **ничего не пишет**: `expanded`, `hidden`, `order`, `sortOrder`, `width`, `minWidth` — геттеры по правилу «сохранённое состояние ?? поле». Значения состояния приходят в `wrapColumns` через `stateOf(key)` — источник у таблицы (её `columnView`/`columnSizing`); обёртка кэшируется по ключу-пути (`Map` инстанса), и при смене поля строится **новая** обёртка, которая заменяет старую в кэше — старая остаётся нетронутой. Записать в обёртку нельзя: под Reactor такая запись прошла бы молча и потерялась бы при следующем сбросе. `treeColumn` — поле с `treeMode`, иначе первое.

**Запись в ячейку — одна точка, обратная чтению.** Значение узла читает `column.valueOf(data)` (путь по `id` предков, затем `container[id]`; объект-узел отдаёт значение под `valueKey`), пишет обратная ей `column.setValueOf(data, value)`: тот же путь, затем `container[id] = value`, а у объекта-узла — `own[valueKey] = value` (дети узла целы; массив — значение, заменяется целиком). Возвращает `true`, если записано, и `false`, если пути нет (родитель не объект, нет данных) — тогда данные не тронуты. Пишется только целевое поле, промежуточные узлы пути не создаются. Ячейка (`cell.setCellValue`) пишет так: строка-дескриптор (настройки, у неё есть `apply`) — через свой `apply` (первым, как и раньше); обычная строка — в **исходный** объект потребителя через `column.setValueOf`. Колонка или строка с `readonly` запись запрещает; то же значение не пишется. Контролл подбирает ячейка: `editorTag` (ячейка → строка → колонка → таблица) приоритетнее, иначе контролл по типу поля колонки (та же карта, что у формы: `column.field.control` / `column.field.type`); он **правится**, а у `readonly` колонки/строки — рисуется только для чтения; нет типа — текст. Ввод из контролла идёт в ячейку только при фокусе внутри (без фокуса программные проталкивания значения отбрасываются). Редактор-посредник (тег без публичного `value`, как роутер настроек) получает `row/column/table` и значение читает сам; редактору со `value` ячейка отдаёт `field`, `value` и `readonly`. После записи в исходный объект ячейка сбрасывает снимок `row.data` (его Reactor строит копией: исходный объект потребителя не реактивен и сам перерисовку не вызывает) — слои (фильтр, сортировка) и ячейки читают свежее значение — и стреляет `cell-changed`.

`columnLayout` — единственный источник представления: `leaves` (плоский pre-order видимых листьев — из них строки строят ячейки), `headers` (строки шапки сверху вниз, ячейки `{node, start, colSpan, rowSpan, level}`, накрытые не отдаются), `maxDepth`, плюс проекция размеров `tracks` и `minTotal`. **Шапка и строки берут один `layout`**.

**Размеры — контракт и одна проекция, а не пиксели в JS.** Правило трека листа: есть числовой `width` → фиксированный трек (он же минимум), иначе `minmax(<min>, 1fr)`, где `min` — числовой `minWidth` или токен `--table-min-col`. `gridTemplate(leaves)` собирает из этого одну строку треков; если все видимые листья фиксированы, добавляется **хвостовой** трек `minmax(0, 1fr)` — служебный `@filler`: это трек, а не колонка (в листья, поиск и состояние он не попадает), фон строки на него красится, а линия между последним листом и хвостом есть. `minTotal` — контракт `{px, flex}` (сумма фиксированных ширин и числовых минимумов + число гибких колонок), в CSS — `calc(Npx + K * var(--table-min-col))`; ширину родителя в JS не считают: он занимает столько треков, сколько листьев под ним (спаны). Таблица кладёт `--table-tracks` и `--table-min-total` на прокручиваемый элемент шаблона, шапка и строки читают их статическим CSS — формула сетки в коде одна, поэтому дрейф шапки и ячеек нулевой. При переполнении (`sum > ширины`) прокручивается контейнер таблицы, а шапка и строки имеют общий `min-width`, поэтому едут вместе; шапка при этом остаётся липкой сверху.

**Состояние колонок — отдельно от метаданных.** Три сохраняемых свойства: `columnSizing` (`{key: {width?, minWidth?}}`), `columnView` (`{key: {expanded?, hidden?, order?, sortOrder?, groupOrder?}}`) и `columnFilter` (`{key: текст}`), все с `$save`; ключ колонки — ключ-путь (`fio/last`). Разделение не косметическое: Reactor сбрасывает зависимости по факту **замены** свойства, поэтому правка ширины пересчитывает только треки, ввод фильтра — только строки, а раскладку не трогает ни то, ни другое. Запись — **только заменой** объекта (через `nextColumnState` / `nextColumnFilter`): `$save` пишет в LocalStorage лишь при присваивании свойства, мутация внутри объекта молча теряется. Публичный API — `setColumnState(key, patch)` и `resetColumnStates()`; `undefined` в patch удаляет значение. Путь хранения — штатный `$saveKey` компонента, его задаёт потребитель по месту использования (`$save` читает хранилище при первом обращении, поэтому `$saveKey` должен быть задан до первого чтения состояния).

**Шапка — орган управления, состояния не хранит.** Клик по заголовку листа — сортировка через `sortBy(key, {add})`: цикл `+N → −N → без сортировки` (чистая `nextSortOrders` + перенумерация без дыр), простой клик — одиночная, Ctrl/Cmd — в мультисортировку; родитель сортируется своим значением (`valueOf` под `valueKey`). Индикатор — `▼N`/`▲N` из `node.sortOrder`. Кнопка-фильтр у листа открывает меню с полем ввода (`ODA.showDropdown` + `oda-text-input`); ввод пишет `columnFilter`, фильтры колонок применяются вместе с глобальным через И. Правый клик в любом месте шапки — временный property-grid настроек (`settings.js`: две колонки, строки называют только ТИП, на колонке значений — роутер; окно не прячется при изменениях). Идеал настроек — `property-grid` таблицы, но его нет до фазы 04 — замена отмечается в этапе 15. Ресайз жестами — этап 9.

## 4. Из чего это состоит

- `table.js` — `oda-table` (каскад колонок: дерево полей WORK → `layout`; слои данных, строки)
- `column-header.js` — `oda-table-header` (липкая многострочная шапка из `layout`: спаны, маркер раскрытия колонки, сортировка кликом с индикатором, кнопка-фильтр с меню, контекстное меню настроек)
- `settings.js` — `oda-table-settings` (временные настройки «в лоб» на живом `oda-table`: дерево строк — узел `columns` тем же деревом, что поля; строки называют только ТИП; идеал — `property-grid`, замена — этап 15)
- `router.js` — `oda-table-router` (ведомство p-g, фаза 04): ставится редактором колонки, ставит настоящие контроллы по типу строки, значение читает сам, синхронизация сходящаяся
- `row.js` — `oda-table-row` (строка: раздаёт ячейки по `layout.leaves`, состояния `focused`/`selected`/`odd`, линии; та же grid-сетка, что у шапки)
- `cell.js` — `oda-table-cell` (рамка ячейки: границы, отступы, обрезка, контур фокуса, место под контролл; выбор редактора `editorTag` — ячейка → строка → колонка → таблица, иначе контролл по типу поля; запись — одна точка `setCellValue` (дескриптор строки или `column.setValueOf`), событие `cell-changed`; фокус разводит потоки) и `oda-table-cell-tree` (`extends`, колонка дерева: спейсер уровня, маркер раскрытия, заглушка)
- `lib/model.js` — слои данных без DOM и WORK; Reactor — опционально (только `Reactor.activate` обёрток, если он есть в глобалях)
- `lib/column.js` — модель колонок: `wrapColumns` (обёртка читает `valueOf` и пишет `setValueOf`), `columnLayout`, `flatColumns`, состояние (`nextColumnState`, `nextColumnFilter`), цикл сортировки (`nextSortOrders`), размеры (`trackOf`, `gridTemplate`, `hasFiller`, `minTotal`, `minTotalCss`)
- `lib/coerce.js` — типизация значения по типу колонки (копия из `table/lib/coerce.js`)
- `index.html` — демо (дерево метаданных, раскрываемая колонка, размеры и минимумы, сортировка/фильтр/настройки от шапки, порядок набором, сохранение настроек, сброс, дерево строк, пустые значения)
- `readme.md` — этот файл + контракт точек входа (§7)

## 5. В каком это состоянии

- ✅ этап 8-a: колонки как дерево полей WORK. Вход — `metadata` (корневые поля `{id, label, type, fields, control, readonly}`, read-only) плюс настраиваемые `valueKey` (деф. `'@'`) и `childrenKey` (деф. `'fields'`). `wrapColumns` строит обёртки `ViewColumn` с ключом-путем (`id`, дубли → `id@N`, вложенные → `parent/id`), ленивыми `children`, `valueOf(data)`, `allowExpand`/`hasChildren`; значение узла: путь по `id` предков, затем ключ поля; объект-узел отдаёт значение под `valueKey`. `columnLayout` — единственный источник: `leaves` + `headers` со спанами.
- 🧪 этап 8-b: размеры колонок и сохраняемое состояние. Правило трека листа (`width` → фиксированный, иначе `minmax(<min>, 1fr)`), одна проекция `gridTemplate(leaves)` → строка треков + хвост `@filler`, когда все листья фиксированы; `minTotal` — контракт `{px, flex}`, в CSS `calc(Npx + K * var(--table-min-col))`, минимум по умолчанию `--table-min-col` (`--space-xl`) задаётся на `:host` таблицы. Таблица ставит `--table-tracks` и `--table-min-total` на прокручиваемый элемент шаблона; `.hgrid`/`.rgrid` читают их статическим CSS, геттеры `gridStyle` убраны — формула сетки одна, дрейф шапки и ячеек нулевой, при переполнении общий скролл и липкая шапка. Обёртки перестали быть хранилищем состояния: `expanded`/`hidden`/`order`/`sortOrder`/`width`/`minWidth` — геттеры «состояние ?? поле», обёртка при смене поля **заменяется** и не пишется (снят K2). Состояние — два сохраняемых свойства `columnSizing`/`columnView` с `$save` и штатным `$saveKey`; запись только заменой объекта через `nextColumnState`, API — `setColumnState(key, patch)`/`resetColumnStates()`. Правка ширины пересчитывает треки, не трогая `layout`. Демо переведено с пересборки метаданных на состояние: метаданные присваиваются один раз, тогглеры/порядок/сортировка/ширины — через API, есть «Сбросить настройки». Тесты: `tests/table-model.test.js`, `tests/table-column.test.js`, `tests/table-coerce.test.js` — 84.
- 🧪 этап 8-c: сортировка, фильтр и меню от шапки. Клик по заголовку — `sortBy(key, {add})`, цикл `+N → −N → без сортировки` (чистая `nextSortOrders`, перенумерация без дыр); индикатор `▼N`/`▲N`; родитель сортируется своим значением (`valueOf` под `valueKey` — `sortCompare` читает значение колонки, а не `data[name]`). Фильтры колонок — третье свойство `columnFilter` с `$save` (ввод по буквам не трогает раскладку), применяются с глобальным через И (`columnFilterPredicate` + `allPredicates`), при фильтре дерево раскрывается виртуально (`hasColumnFilter` в `forceExpand`). Кнопка-фильтр у листа — меню с полем ввода (`ODA.showDropdown` + `oda-text-input`, живой ввод). Правый клик в любом месте шапки — временные настройки «в лоб» (`settings.js`: дерево строк — узел `columns` тем же деревом, что поля — дочерние колонки вложенностью, у каждой параметры Скрыта/Ширина/Порядок/Сортировка/Фильтр/Раскрыта — плюс свойства таблицы Поиск/Зебра/Фокус/Линии/Строки; строки называют только ТИП, на колонке значений — роутер `router.js`, контроллы настоящие; окно не прячется; идеал — `property-grid`, замена — этап 15). `groupOrder` читается из состояния (показ групп — позже). Демо без тогглеров и селекта сортировки. Тесты: `tests/table-model.test.js`, `tests/table-column.test.js`, `tests/table-coerce.test.js` — 110.
- Ещё нет: ресайза жестами, `maxWidth` и `fix`-колонок (9); `fitColumn` (кандидат в 9); полного правила `type` → контрол, чисел вправо и формата (этапы 10–11); чекбокса селекта и счётчика детей (12); панели детализации (13); виртуализации и точной высоты строки (14); меню настроек и его доводка, чистка ключей, `$saveKey` по умолчанию, замена меню на `property-grid` (15, сохранение уже есть с 8-b). ## 7. Контракт точек входа (этапы 8-a, 8-b, 8-c)

Вход:

| Свойство | Тип | Смысл |
|---|---|---|
| `dataSet` | Array | строки; таблица сама их не меняет, **кроме правки в ячейке**: она пишется в исходный объект строки (см. «Запись в ячейку») и сообщается `cell-changed` |
| `metadata` | Array | дерево полей WORK: `{id, label, type?, control?, editor?, readonly?, fields?, expanded?, hidden?, order?, width?, minWidth?, treeMode?, sortOrder?, groupOrder?}`. `id` — ключ значения и данных; `label` — подпись (иначе `id`); `editor` — тег редактора на всю колонку (так стоит роутер p-g); дети — `fields` (не `items`); `readonly` — колонку не править (ячейка рисует контролл только для чтения и не пишет; то же — у строки с `data.readonly`); `expanded`/`hidden`/`order`/`sortOrder`/`groupOrder` — **стартовые** значения, их перекрывает сохранённое состояние; `width`/`minWidth` — размеры (см. ниже); `treeMode` — главная колонка (скрыть нельзя). **Метаданные не мутируются** — состояние живёт в свойствах таблицы |
| `defaultEditor` | String? | тег редактора ячеек по умолчанию (ячейка → строка → колонка → таблица); не задан — текстовые |
| `valueKey` | String | ключ значения объекта-узла (деф. `'@'`, контракт DataAccessNode): `data.fio['@']` — значение, `data.fio.last` — ребёнок; скаляр отдаётся сам; отсутствие — `undefined` |
| `childrenKey` | String | ключ детей поля (деф. `'fields'`) |
| `filter` | String | глобальный поиск (регистр не важен): по дереву колонок, включая **вложенные поля** свёрнутой колонки (значение берётся через `valueOf` — путь по `id`). При значении дерево строк раскрывается виртуально на полную глубину (см. `filterForceExpanding`); пусто — поиск не выполняется вовсе |
| `filterForceExpanding` | Boolean | по умолчанию `true`: активный `filter` раскрывает всё дерево и фильтрует целиком, не меняя `expanded`; на время фильтра экспандер выключен. `false` — искать только по собранным ветвям (для асинхронных детей) |
| `allowFocus` | Boolean | клик по строке делает её текущей (системный маркер `focused`); по умолчанию выключено, как у `oda-table` |
| `evenOdd` | Boolean | зебра: чётность от позиции в окне (`screenTopRowIndex + index`), как у `oda-table`; нечётные строки получают наследуемую `--row-surface` (фон ячейки), тон `color-mix(… var(--content-color) 8% …)`; состояние строки рисует ячейка, т.к. фон на `:host` строки перекрыт её непрозрачным фоном |
| `colLines` / `rowLines` | Boolean | линии между колонками и строками: `1px solid var(--header-background)` у ячейки, `1px solid var(--subtle-border)` у шапки; правой линии у последней колонки нет (`start + colSpan === N` у шапке, `last` у ячейки) — поэтому сетка совпадает (дрейф 0); при хвосте `@filler` последняя колонка краем сетки не считается, линия между ней и хвостом рисуется |
| `focusedRow` | Object | текущая строка (сырой объект данных); ставится кликом по строке, при `allowFocus` |
| `columnSizing` | Object | **сохраняется** (`$save`): `{[ключ колонки]: {width?, minWidth?}}`. Ключ — ключ-путь колонки (`fio/last`). Задавать извне не нужно: пишите через `setColumnState` |
| `columnView` | Object | **сохраняется** (`$save`): `{[ключ колонки]: {expanded?, hidden?, order?, sortOrder?, groupOrder?}}`. `sortOrder: 0` — явное «без сортировки» (перекрывает метаданные). Задавать извне не нужно: пишите через `setColumnState` |
| `columnFilter` | Object | **сохраняется** (`$save`): `{[ключ колонки]: текст}` — фильтры колонок. Применяются вместе с глобальным `filter` через И; пустой текст — отсутствие (ключ удаляется). Отдельно от `columnView`: ввод по буквам не пересобирает раскладку. Задавать извне не нужно: пишите через `setColumnState(key, {filter})` |

`columns` больше нет: вход колонок — только `metadata`.

### Размеры колонок

| Что | Правило |
|---|---|
| фиксированная | `width` в метаданных или состоянии → трек ровно этой ширины, минимум тот же |
| гибкая | без `width` → `minmax(<min>, 1fr)`: остаток делится поровну, но не уже минимума |
| минимум | `minWidth` числом, иначе `--table-min-col` (на `:host` таблицы = `var(--space-xl)`; переопределяется на месте) |
| переполнение | сумма минимумов больше ширины → горизонтальный скролл у контейнера таблицы; шапка и строки одной ширины и едут вместе |
| родитель | ширина родителя = сумма детей: спаны в сетке, JS её не считает |
| `@filler` | если все видимые листья фиксированы — добавляется хвостовой трек `minmax(0, 1fr)`; это трек, а не колонка: фон строки на него красится, линия между последним листом и хвостом есть |

### Состояние колонок: API

| Имя | Форма | Смысл |
|---|---|---|
| `setColumnState(key, patch)` | `key` — ключ-путь колонки; `patch` — `{width?, minWidth?, expanded?, hidden?, order?, sortOrder?, groupOrder?, filter?}` | записать состояние; `undefined`/`null` удаляют значение (у `filter` — и пустой текст); размеры, вид и фильтры пишутся в разные свойства, заменой объекта |
| `sortBy(key, {add})` | `key` — ключ-путь; `add` — добавить в мультисортировку (Ctrl/Cmd) | клик шапки: цикл `+N → −N → без сортировки`; без `add` — одиночная (остальные в `0`), с `add` — в набор с перенумерацией |
| `showSettings(anchor)` | событие или элемент | временные настройки «в лоб» (`settings.js`): дерево строк — `columns` с параметрами + свойства таблицы; кнопки «Показать все», «Снять сортировку», «Сбросить настройки»; главная колонка в список видимости не попадает; окно при изменениях не прячется; идеал — `property-grid` (фаза 04), замена — этап 15 |
| `resetColumnStates()` | — | сбросить всё к метаданным |
| `$saveKey` | строка, задаётся потребителем | путь хранения состояния (`host._savePath/localName[$saveKey]`). **Задайте до первого чтения состояния** — `$save` читает хранилище один раз, когда кэш пуст. Без него все таблицы на странице делят одно хранилище |

Писать состояние вручную (`grid.columnView[key] = …`) нельзя: `$save` сохраняет только присваивание свойства, а вложенная мутация теряется молча. Метаданные при этом остаются read-only — состояние никогда не пишется в них и в обёртки колонок.

CSS-переменные компонента: `--table-tracks` (строка треков), `--table-min-total` (минимальная ширина сетки), `--table-min-col` (минимум гибкой колонки, задаётся на `:host`, токен по умолчанию `var(--space-xl)`).

Внутри (не контракт): `screenTopRowIndex` — верхняя строка окна (скролл — этап 14); строки слоя — ViewRow `{data, level, expanded, items}`; `gridVars`/`hasFiller` — проекция сетки на элемент шаблона и признак хвоста.

Выход (события и методы появятся с этапами механик; имена — как у `oda-table`):

| Имя | Форма | Этап |
|---|---|---|
| `cell-changed` | `detail.value = {row, column, value}` (обёртка `detail.value` — общая для `fire` ядра): `row` — исходный объект данных строки, `column` — колонка (`ViewColumn`; ключ `column.key`, поле `column.field`), `value` — записанное значение | уже есть: правка в ячейке обычной строки (всплывает, `composed`). Не стреляет, если значение не изменилось, колонка/строка `readonly` или записать некуда; строки-дескрипторы (настройки) пишутся через свой `apply` и событие не стреляют |
| `checked-changed` | `{row, state}` | дерево/отметка |
| `setChecked` / `checkedOf` | методы | уже есть: отметка строки (событие и каскад по дереву — этап 12) |
| `sortBy` / `showSettings` | методы | уже есть: сортировка от шапки и меню настроек (8-c) |
| `setCell` / `moveColumn` / ... | методы | свои этапы |

Правила каркаса: компоненты — через `imports`; исключение на этапе разработки — ленивые модули настроек (`settings.js` и его цепочка грузятся по правому клику; решение 2026-10-12 — держать частями в отдельных модулях, разобрать ближе к концу); стили — только системой; геттеры без записи; пустое — `undefined`.
