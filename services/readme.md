# SERVICES — внешние сервисы-коннекторы

## Что это

Класс-каталог внешних интеграций (поиск, погода, почта, 1С…). Каждый провайдер — дочерний класс с метой `$service`. Техническое измерение — коннекторы с единой схемой вызова; прикладное — глаза и руки агента во внешнем мире.

## Зачем это нужно

Агенты не должны знать провайдеров поимённо: выбор идёт по реестру и `capabilities`, а не по хардкоду. Новый сервис подключается одним классом, без правок агентов. Правила заимствованы из DeepSeek Harness (`adding-a-tool.md`): схема первична, аргументы проверяются до вызова, канонический результат отдельно от человеческой сводки.

## Как это работает

1. **Контракт провайдера** (`SERVICES/<Имя>/$service/class.js`): `label/description/icon`, `capabilities[]` (словарь возможностей: `search`, `fetch_url`, `weather`…), `SCHEMA` (`{метод: {description, params: {type, properties, required}}}`), сами `async`-методы. Методы возвращают канонический JSON (`{…данные}`) или `{error}` — никогда исключения наружу и никогда прозу вместо полей (id — в поле, не в тексте).
2. **Реестр** — `services_schema()` на классе `SERVICES` (`sources/server/folder.js`, рядом с `get_schema`): сводит всех провайдеров в `{services: [{service, path, label, description, icon, capabilities, tools}]}`. Провайдеры без `SCHEMA` и без `capabilities` в сводку не попадают.
3. **Discovery**: `web` берёт провайдеров с `tools.search`, `site` — с `tools.fetch_url` из реестра; захардкоженные пути — только fallback, если реестр пуст.
4. **Валидация до `exec`** (`validateCall` в `prompt/$method/class.js`): обязательные поля `SCHEMA.params.required` проверяются до вызова; провал — guided-подсказка с `state`, без `error` (вид ≠ ошибка). Внутри метода аргументы уже правильные — дополнительных проверок не дублировать.
5. **Правило value/render**: канонический JSON результата — для кода (`exec` возвращает как есть); человеческая сводка — в `content` блока; состояние/UI — в `state`/`path`. UI-форматирование (fence, пути-ссылки) в каноническое значение не подмешивать.

## Из чего это состоит

- `class.js` в `$service/` — тип `$service`: `icon`, `description`, `METADATA.FIELDS` (`baseUrl`, `apiKey`, `capabilities`) (конфигурация подключения, шаблон провайдера)
- `mcp_list_tools` / `mcp_call_tool` — stdio-клиент MCP в типе (наследники задают `mcp: {command, args, env}` и получают вызовы; `secret:ФАЙЛ` — через `read_secret`) (протокол без новых зависимостей)
- `DuckDuckGo/`, `Yandex/`, `SearXNG/` — поиск (`search`) и чтение страниц (`fetch_url`) (глаза интернета)
- `Weather/` — погода (`get_weather`) (сенсор внешнего мира)
- `ArgoCD/`, `1C/` — прикладные провайдеры со своей `SCHEMA` (интеграции бизнеса)
- `services_schema()` — реестр для агентов (точка discovery, замена хардкода путей)

## В каком это состоянии

- ✅ контракт провайдера (`capabilities/SCHEMA/METADATA`), 6 провайдеров
- ✅ реестр `services_schema()` + discovery в `web`/`site` + `validateCall` до `exec`
- ✅ MCP-клиент (stdio JSON-RPC в типе) + агент `mcp` (search/inspect/install, установка — через `work` с approval)
- 🔧 внешние MCP-серверы поверх HTTP/SSE, версионный пин пакетов — не реализовано
- 🔧 `result.error` от сервисов агенты местами помечают `error` — долг: различать провал операции и подсказку

## Дальнейшие планы

- Внешние MCP-серверы как провайдеры (клиент + политика доверия).
- Агрегация политик pre/post-execute (allow/deny/ask) поверх реестра.
- Связка телеметрии вызовов с единым журналом (`register/`).
