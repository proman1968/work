## 0. Суть

- WORK = дерево организации ($base и ниже) с **рабочими местами**; к местам прилинкованы классы трёх слоёв (как в ODANT): **справочники**, **операции**, **счета журнала**. Ссылка места = права + меню сотрудника.
- Операции — единое дерево наследования (общая операционная модель). Лист — однозначный набор проводок.
- Любая операция (не только бухгалтерская) попадает в **единый журнал** с нормативной стоимостью/количеством → сквозная аналитика, траектории и мгновенные состояния любых объектов.
- **Метаданные — файлы** (class.js, handlers, skills, печатные шаблоны, места), **данные — SQLite** (объекты, версии, проводки).
- Новый пользовательский интерфейс — **Lit + Web Awesome** (локально, без сборки), старый проводник на ODA — «Конфигуратор» (судьба решится после показа).
- Агентская система не урезается, но эти 2 недели не развивается (кроме инструментов работы с данными).

## 1. Решения по модели (ADR)

**Р1. Жизненный цикл операции.**
`черновик` (правится, проводок нет, в отчётах не существует) → `зарегистрирована` (проводки созданы в той же транзакции, объект неизменяем) → `исправлена` (новая версия: сторно проводок прежней версии + новые проводки в одной транзакции; обе версии хранятся; если дата в закрытом периоде — сторно и новые проводки текущей датой) / `отменена` (сторно всего).
Флаг класса `AUTO_REGISTER: true` — регистрация сразу при создании (письмо, звонок; создаёт человек, ИИ или триггер).

**Р2. Проводки — набор правил, наследуемый по дереву операций.**
Правило: `{ id, each?, debit: {account, analytics}, credit: {account, analytics}, amount, qty?, qty2? }`.
- Правила сливаются по `id` от корня к листу (напр. «Платежи с р/с» задают Кт 51, лист «Поставщику» — Дт 60).
- Лист обязан быть полностью определён (проверка при сохранении класса / синхронизации).
- `each: '<табличное поле>'` — проводка на каждую строку (ведомость зарплаты: начисление + налоги по каждому сотруднику, + сводная управленческая проводка).
- Выражения — **безопасный мини-язык** (не JS): арифметика, поля операции, `row.*`, `round/min/max/if/sum/abs`, `norm()`, `coef()`.

```js
POSTINGS: [
  { id: 'accrual', each: 'staff', debit: { account: '26' }, credit: { account: '70', analytics: { employee: 'row.employee' } }, amount: 'row.sum' },
  { id: 'taxes',   each: 'staff', debit: { account: '26' }, credit: { account: '69' }, amount: "round(row.sum * norm('Ставка страховых взносов'), 2)" },
  { id: 'mgmt',    debit: { account: 'labor' }, credit: { account: 'payroll' }, amount: 'sum(staff.sum)' },
]
```

**Р3. Табличные части.** Тип поля `Table` с вложенными `FIELDS` (включая `Link`). Строки — внутри тела объекта.

**Р4. Нормативы и ставки — через счета.** Справочник «Виды нормативов»; счёт «Нормы» с аналитиками «вид норматива» и «объект»; операция «Установка норматива» проводит дельту. `norm('Вид', объект?)` = сальдо на дату операции. История нормативов = журнал. Ставки (взносы, НДС) — тоже нормативы.

**Р5. Автоаналитики каждой проводки:** автор, рабочее место, подразделение, операция, класс операции — колонки с индексами.

**Р6.** Классы общие (`/DATA`), данные разделяются аналитикой подразделения. Локальные наследники классов у подразделений — позже.

**Р7. Ссылки и время — без снимков, с версиями во времени.**
- Link хранит `id` (+ класс). Версии объекта имеют `valid_from` → чтение «как было на дату»; ссылка в операции показывается в состоянии на дату операции.
- Реальные справочники с наследованием: «Субъекты» → «Юр. лица», «Физ. лица» (запрос к родителю возвращает объекты потомков).
- Виртуальные справочники («Клиенты»): состав на дату — по сальдо счёта; собственные поля — записи-расширения (`ext_of`) с версиями.
- Поле может ссылаться на виртуальный справочник: выбор ограничен составом на дату операции, хранится id реального объекта.

**Р8. Видимость — `scope` на ссылке рабочего места:** `own` (свои) | `place` (своего места) | `unit` (подразделения и ниже) | `all`.
По умолчанию: справочники `all`, операции и счета `unit`. BOSS — своё поддерево на чтение, ADMIN — всё. Реализация — один SQL-фильтр по колонке подразделения против списка потомков.

**Р9. Количество и единицы.** Проводка хранит `qty` в базовой единице номенклатуры + `doc_qty/doc_unit` для показа; у номенклатуры табличная часть «Единицы» (единица, коэффициент, цена); `qty2` — второе измерение (масса при учёте топлива в литрах через плотность партии).

**Р10.** Всё, что не проведено, не существует (или черновик). Отчёты и состояния — только по зарегистрированным операциям.

**Р11. Типовая конфигурация с печатными формами.** Шаблоны — файлы в метапапке класса операции (`$operation/print/*.html|docx`), наследуются вниз через `~`. Печать: HTML → PDF (`export_pdf`), DOCX (`render_doc`).

**Р12. Единый журнал.** Журнал один; «бухгалтерские», «управленческие» и т. п. счета — это просто разные коды/названия и разные ссылки рабочих мест (бухгалтер видит бухгалтерские). Счета ссылаются по стабильному `cid` (код), не по пути.

**Р13. Хранилище.** Одна БД `.data/work.db` (источник истины, бэкап обязателен). RAG — отдельно в `.index/work.db` (пересобираемый).

**Р14. Поставка.** Кроссплатформенно: служба Windows и systemd на Linux. ИИ — любой провайдер (локальный llama.cpp/vLLM, сервер в контуре, облако). Система всегда внутри ЛВС организации (видит папки, 1С и т. д.). Для комплекта «под ключ» — мини-ПК с Qwen 3.8 27B.

**Р15. Орг-навигация.** Пользователь может работать в нескольких подразделениях/местах (руководители). В шапке — понятный навигатор: дерево «мои подразделения и места», хлебные крошки, переключение контекста; руководитель проваливается в подчинённые подразделения (сводный вид поддерева). Контекст (подразделение, место) определяет меню и фильтры.

## 2. Схема БД (`.data/work.db`)

```sql
classes (cid PK, path, parent, type, label, schema JSON)        -- кэш из class.js
class_tree (ancestor, descendant, depth)                        -- замыкание иерархии

objects (id PK, cid, status, time, author, place, unit, ext_of, version, body JSON)
object_versions (id, version, valid_from, author, body)
refs (obj_id, field, row, ref_id, ref_cid)                      -- обратные ссылки
objects_fts (FTS5)                                              -- полнотекстовый поиск

entries (id PK, op_id, op_version, rule, row, time,
         debit_cid, credit_cid, amount INTEGER /*копейки*/, qty, qty2,
         doc_qty, doc_unit, author, place, unit, op_cid, storno)
entry_analytics (entry_id, side 'D'|'C', slot, ref_id, ref_cid)

settings (key, value)                                           -- дата закрытия периода и др.
```

Индексы: `entries(debit_cid,time)`, `entries(credit_cid,time)`, `entries(unit,time)`, `entries(op_id)`, `entry_analytics(ref_id)`, `objects(cid,time)`, `objects(ext_of)`.
Итоги по родительскому счёту/классу — запрос по потомкам из `class_tree`; физический сбор вверх не нужен.

- **Демо-организация:** Директор; Отдел продаж (руководитель, менеджеры); Закупки; Склад (кладовщик); Логистика (логист, водители); Бухгалтерия (главбух, бухгалтер). Места со ссылками и `scope`. Демо-данные за 3 месяца (`scripts/seed-demo.mjs`).
