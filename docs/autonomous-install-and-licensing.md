# Механика установки, автообновления и лицензирования автономных машин ODANT-WORK

Документ описывает полный жизненный цикл развёртывания, автоматического обновления через `npm`, лицензирования и криптографической защиты автономных комплексов **ODANT-WORK** на базе платформы **AMD Ryzen™ AI Max+ PRO 495 (192 ГБ Unified RAM, SSD 4 ТБ)**.

---

## 1. Установка и безопасное автообновление через `npm` (`sources/host/auto-updater.js`)

### 1.1. Первичная установка и запуск
Платформа устанавливается и запускается через пакет `odant-work` из реестра `npm`:
```bash
npm install -g odant-work
odant-work
```
или непосредственно в рабочей директории сервера:
```bash
npx odant-work
```
При старте сервер (`run.mjs` → `sources/work.js`):
1. Проверяет актуальность зависимостей и при необходимости докачивает их (`npm i --production`).
2. Создаёт в `#system/package-manifest.json` криптографический манифест базовой поставки (`{ [relPath]: sha256 }`) для всех системных файлов и коробочных классов текущей версии.
3. Открывает веб-приложение в браузере (`http://localhost:8001/`).
4. Запускает фоновый демон периодической проверки обновлений `startAutoUpdateDaemon()` (по умолчанию каждые 6 часов).

### 1.2. Как автообновление сохраняет базы, файлы, настройки и изменённые классы
При обнаружении новой версии в `npm` (`checkForNpmUpdates` / `checkAndApplyNpmUpdate`) система скачивает релизный архив `.tgz`, проверяет его контрольную сумму и применяет обновление по алгоритму `applyUpdateFromDirectory`:

1. **Неприкасаемые пользовательские зоны (`isProtectedUserPath`):**
   Следующие пути **никогда не перезаписываются и не удаляются** при любых обновлениях:
   * Системная папка и настройки узла: `/#system/**`, `**/#system/**`, `**/#secret/**`, `config.json`, `.env*`;
   * Все базы данных SQLite и индексы: `**/*.db`, `**/*.db-wal`, `**/*.db-shm`, `.data/**`, `.index/**`, `**/.RAG/**`;
   * Организации пользователей: `ORGANIZATIONS/<ИмяОрганизации>/**` (включая их подразделения `$structure`, роли, ссылки `LINKS` и локальные БД `<Организация>/$base/#system/work.db`);
   * Профили и личные кабинеты пользователей: `USERS/<uid>/**`;
   * Скачанные веса локальных моделей, датасеты и обученные адаптеры: `**/#weights/**`, `**/#datasets/**`, `**/#adapters/**`, `**/*.safetensors`, `**/*.gguf`, `**/*.onnx`;
   * Рабочие файлы, документы, задачи и логи в зонах ролей: `**/$*/DATA/**`, `**/$*/ADMIN/**`, `**/$*/BOSS/**`, `**/$*/USER/**`, `**/$*/work/**`, `**/logs/**`, `**/history/**`.

2. **Сохранение изменённых пользователем классов (`MODULES/**`, `$server/**`, `MODELS/**`, `SERVICES/**`):**
   * Для каждого файла из нового релиза система сверяет текущий `SHA-256` файла на диске с хешем оригинальной поставки из `#system/package-manifest.json`.
   * Если `sha256(на диске) === sha256(в манифесте старой версии)` — пользователь не менял этот класс/файл, и он автоматически обновляется до новой версии.
   * Если `sha256(на диске) !== sha256(в манифесте старой версии)` — **пользователь доработал этот класс или файл**:
     * Пользовательский файл на диске **остаётся нетронутым** (попадает в список `preservedUserModified`);
     * Новая эталонная версия из пакета аккуратно сохраняется рядом в `#system/updates/upstream-<version>/<путь>` для справки;
     * Никакие созданные пользователем собственные классы или файлы не удаляются.

3. **Обновление системного ядра (`isCoreEnginePath`):**
   * Системный движок (`sources/**`, `oda/**`, `run.mjs`, `package.json`) обновляется всегда, чтобы система получала исправления и новые возможности ядра.

## 2. Режим работы сразу после установки (до получения базовой лицензии)

1. После локальной установки и старта в браузере регистрируется **первый пользователь**, который автоматически назначается руководителем всего сервера — **`BOSS` для всего `WORK`** (`ensureBootstrapBoss` в `sources/host/auth-methods.js`).
2. Пока в папке `#system` нет валидной подписанной первичной постоянной лицензии (`baseLicensed: false`):
   * **Вся учётная, документная, коммуникационная и офисная функциональность полностью работает:** создание организаций, подразделений, справочников, планов счетов, проведение операций, отчёты («Ведомость», «Анализ счёта», «Обороты», «Журнал проводок»), чаты, календарь, почта, встроенный локальный Office и конструктор классов.
   * **Ограничение сессий:** доступна только **1 одновременная сессия (`BOSS`)** для первичной настройки системы (`unlicensedBossSeats: 1`). Вход других сотрудников блокируется до активации базовой лицензии.
   * **Отключение агентских функций (`aiAgentsEnabled: false`):** запуск основного ИИ-агента, ролевых субагентов, ИИ-консультанта и фоновых агентских задач заблокирован на уровне ядра (`assertAgentSystemLicensed()` выбрасывает ошибку с кодом `LICENSE_REQUIRED`).

Все ограничения снимаются при получении **первичной постоянной лицензии**, после чего в любой момент могут докупаться дополнительные временные лицензии:

|---|---|---|---|---|
| **Базовый комплект (Машина + Базовая лицензия)** | `WORK-PAK-495-192-4T` | Постоянная (вечная) | Сервер AMD Ryzen™ AI Max+ PRO 495 (192 ГБ RAM, 4 ТБ SSD) + **10 вечных конкурентных мест** + включение агентской ИИ-системы + 1 год поддержки Enterprise | **5 000 000 ₽** |
| **Базовая постоянная лицензия (без железа)** | `WORK-LIC-BASE-10` | Постоянная (вечная) | Для самостоятельно приобретённых машин: **10 вечных конкурентных мест** + снятие блокировки агентской ИИ-системы + 1 год поддержки Enterprise | **4 000 000 ₽** |

## 4. Личный кабинет `work.odant.org` и способы оплаты

1. Будущий владелец локальной системы регистрируется на сайте **`work.odant.org`**, подписывает публичную оферту простой электронной подписью (ПЭП) и попадает в личный кабинет.
2. В личном кабинете доступны два способа оплаты любого заказа (`POST /api/orders/checkout`):
   * **Способ 1: Онлайн через ЮKassa (`paymentMethod: 'yookassa'`)** — оплата картой, СБП или B2B-платежом с чеком по 54-ФЗ. Сразу после получения webhook `payment.succeeded` лицензии автоматически выпускаются в личном кабинете.
   * **Способ 2: Оплата по договору / счёту для юридических лиц (`paymentMethod: 'invoice'`)**:
     * Система автоматически формирует номер договора (`ДОГ-...`), номер счёта (`СЧ-...`) и печатную форму **Счёта-договора** (`GET /api/orders/:orderId/invoice`) с реквизитами поставщика и покупателя;
     * Заказ переходит в статус `awaiting_invoice`;
     * После поступления безналичной оплаты подтверждение счёта в админ-панели (`POST /api/admin/orders/:orderId/confirm-invoice`) автоматически выпускает подписанные файлы лицензий в личном кабинете владельца.

## 5. Токен владельца с URL сервера поддержки и файлы лицензий в `#system`

### 5.1. Самодостаточный токен владельца (`owk1.<payload>.<signature>`)
В личном кабинете `work.odant.org` владелец генерирует **токен привязки** (`POST /api/cabinet/token`).
Формат токена:
```text
owk1.<base64url(JSON_payload)>.<base64url(Ed25519_signature)>
```
Внутри `payload` закодированы и подписаны закрытым ключом центра сертификации ODANT:
* `hubUrl` — актуальный URL сервера поддержки (например, `https://work.odant.org`), чтобы локальная система всегда знала, куда обращаться за лицензиями и поддержкой;
* `accountId` и `email` — идентификатор аккаунта владельца в личном кабинете;
* `tokenId` и `secret` — ключ авторизации для скачивания лицензий (при необходимости токен можно перевыпустить/отозвать в ЛК).

**Переезд сервера поддержки на другой домен:**
* Если сервер поддержки переехал на новый домен, новый сгенерированный в ЛК токен уже содержит новый `hubUrl`.
* Если сервер переезжает уже после того, как токен привязан к локальной системе, при очередной синхронизации сервер возвращает в ответе поле `canonicalHubUrl`, и локальный WORK автоматически обновляет сохранённый URL в `#system/owner-token.json`.

### 5.2. Привязка токена и хранение файлов лицензий в `#system`
1. Владелец вставляет токен `owk1...` в раздел **«Лицензирование»** своей локальной системы WORK (метод `license_bind_token` / функция `bindOwnerTokenAndSync`).
2. Локальный WORK проверяет криптографическую подпись токена, сохраняет его в `#system/owner-token.json`, извлекает `hubUrl` и запрашивает свои лицензии (`POST <hubUrl>/api/license/sync-by-token`), передавая свой аппаратный отпечаток (`HWID` + `#system/node-key.json`).
3. Сервер поддержки возвращает отдельные подписанные файлы лицензий, которые сохраняются непосредственно в папке **`#system`**:
   * `#system/license-base-<licenseId>.lic.json` — **файл первичной постоянной лицензии** (`kind: 'base'`, `perpetual: true`, `seats: 10`, `aiAgentsEnabled: true`, `ownerAccountId`);
   * `#system/license-addon-<subId>.lic.json` — **отдельные файлы каждой дополнительной временной лицензии** (`kind: 'addon'`, `perpetual: false`, `seats: N`, `years: 1..5`, `expiresAt`, `ownerAccountId`).
4. Локальный WORK периодически (раз в час в фоне и по кнопке «Проверить лицензии») опрашивает личный кабинет по токену и автоматически докачивает в `#system` новые или продлённые файлы лицензий.

## 6. Криптографическая защита от подделки `license-server`

Так как архитектура `license-server` известна (или может быть развёрнута третьими лицами на стороннем сервере с любым доменным именем), применяется строгая асимметричная схема **Ed25519 Public Key Pinning**:

### 6.1. Почему сторонний `license-server` не может выдать рабочую лицензию или токен
1. **Закрытый ключ (`Private Key`) никогда не входит в код или npm-пакет:**
   * Закрытый ключ центра сертификации (`WORK_AUTHORITY_PRIVATE_KEY`) хранится **исключительно в секретном окружении боевого сервера `work.odant.org`**.
   * В `production`-режиме (`NODE_ENV=production`) `license-server/src/crypto.js` запрещает автогенерацию случайных ключей и требует явной передачи `WORK_AUTHORITY_PRIVATE_KEY`.
   * Сам пакет `work-license-server` помечен `"private": true` в `license-server/package.json`.
2. **Жёсткий пиннинг публичного ключа в клиенте (`TRUSTED_AUTHORITY_PUBLIC_KEYS` в `sources/modules/license/index.js`):**
   * В клиентский пакет `odant-work` жёстко вшиты только два официальных публичных ключа Правообладателя ODANT: основной боевой (`ODANT_AUTHORITY_PUBLIC_KEY`) и резервный холодный (`ODANT_BACKUP_PUBLIC_KEY`).
   * Функции проверки `verifyOwnerAccessToken()`, `verifyLicenseFile()` и `verifyLicenseCertificate()` проверяют подпись `Ed25519` **исключительно против вшитого списка `TRUSTED_AUTHORITY_PUBLIC_KEYS`**.
   * Поле `issuerPublicKey`, приходящее внутри JSON файла лицензии или токена, **никогда не используется как источник доверия**.

### 6.2. Что происходит при попытке подделки
Если злоумышленник развернёт копию `license-server` на своём домене `https://fake-license.example.com`:
* Его сервер сгенерирует собственную пару ключей `Ed25519` (так как не знает закрытого ключа `WORK_AUTHORITY_PRIVATE_KEY` Правообладателя).
* При попытке привязать выпущенный им токен `owk1...` локальный WORK проверит подпись токена через `ODANT_AUTHORITY_PUBLIC_KEY` и **отклонит токен с ошибкой `UNTRUSTED_LICENSE_SERVER` ещё до выполнения сетевого запроса**.
* При попытке вручную положить файл `.lic.json` или `license.json`, подписанный чужим сервером, в папку `#system`, функция `loadLocalLicense()` / `evaluateLicenseState()` обнаружит несовпадение подписи с `TRUSTED_AUTHORITY_PUBLIC_KEYS`, проигнорирует поддельный файл и оставит систему в неактивированном состоянии (`baseLicensed: false`, `aiAgentsEnabled: false`, `totalSeats: 1`).

## 7. Где находятся ключевые файлы реализации

* `sources/host/auto-updater.js` — манифест поставки `#system/package-manifest.json`, проверка релизов в `npm` и безопасное обновление с сохранением пользовательских баз, файлов, настроек и изменённых классов.
* `sources/modules/license/index.js` — клиентское ядро лицензирования, пиннинг `TRUSTED_AUTHORITY_PUBLIC_KEYS`, проверка токена `owk1...`, чтение/запись файлов `*.lic.json` в `#system`, блокировка агентской системы до базовой лицензии (`assertAgentSystemLicensed`) и контроль сессий (`assertWorkplaceAvailableForLogin`).
* `$server/$folder/$class/$structure/$server/handlers/pages/form/license/$handler/license.js` — интерфейс управления лицензиями, привязки токена владельца и автообновления в проводнике WORK.
* `license-server/src/crypto.js` — криптографическое ядро центра сертификации `work.odant.org` (подпись токенов `owk1...`, файлов `.lic.json` и сертификатов).
* `license-server/src/catalog.js`, `license-server/src/store.js`, `license-server/src/server.js` — каталог продуктов (комплект 5 млн ₽, базовая лицензия без железа 4 млн ₽, срочные лицензии кратно годам), оплата через ЮKassa и по счёту-договору для юрлиц, выдача токенов и синхронизация лицензий.
* `tests/license-and-deploy.test.js` — комплексные автоматические тесты всех сценариев (включая защиту от поддельного `license-server` и автообновление через `npm`).
