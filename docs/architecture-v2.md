# WORK v2: учётное ядро и рабочие места

Архитектурные решения, согласованные 25.10.2026. Дополняют [`whitepaper.md`](/whitepaper.md/~/handlers/pages/form/) (онтология) и заменяют раздел хранения объектов из [`docs/storage-architecture.md`](/docs/storage-architecture.md/~/handlers/pages/form/) (JSON-файлы `DATA/` и индексы `INDEX/` у классов).

---

## 1. Суть

- Дерево организации (`$base` и ниже) состоит из подразделений с **рабочими местами**. К местам прилинкованы классы трёх слоёв — **справочники**, **операции**, **счета** единого журнала. Ссылка места одновременно даёт права и задаёт меню сотрудника.
- **Операции** образуют одно дерево наследования — общую операционную модель организации. Лист дерева задаёт однозначный набор проводок.
- **Любая операция**, не только бухгалтерская (письмо, звонок, отпуск, выпуск продукции), попадает в единый журнал с нормативной стоимостью и/или количеством. Финансовый и управленческий контуры сходятся в одну модель, и по любому аналитическому объекту доступны траектория во времени и состояние на момент.
- **Метаданные — файлы** дерева: `class.js`, handlers, навыки, печатные шаблоны, рабочие места. **Данные — SQLite** (`.data/work.db`): объекты, версии, проводки.

## 2. Решения

### Р1. Жизненный цикл операции

| Статус | Смысл |
|---|---|
| `draft` | Черновик: правится, проводок нет, в отчётах не существует |
| `registered` | Факт: проводки созданы в той же транзакции, что и регистрация; объект неизменяем |
| `registered` + новая версия | Исправление: сторно проводок прежней версии и новые проводки — одной транзакцией; обе версии хранятся. Если дата операции в закрытом периоде, сторно и новые проводки датируются текущим днём |
| `cancelled` | Отмена: сторно всех проводок |

Флаг класса `AUTO_REGISTER: true` — регистрация сразу при создании (письмо, звонок), кто бы ни создавал: человек, ИИ или триггер.

### Р2. Проводки — набор правил, наследуемый по дереву операций

```js
POSTINGS: [
  { id: 'accrual', each: 'staff', debit: { account: '26' },
    credit: { account: '70', analytics: { employee: 'row.employee' } }, amount: 'row.sum' },
  { id: 'taxes', each: 'staff', debit: { account: '26' }, credit: { account: '69' },
    amount: "round(row.sum * norm('Ставка страховых взносов'), 2)" },
  { id: 'mgmt', debit: { account: 'labor' }, credit: { account: 'payroll' }, amount: 'sum(staff.sum)' },
]
```

- Правила сливаются по `id` от корня к листу: «Платежи с р/с» задают Кт 51, лист «Поставщику» дописывает Дт 60.
- Лист обязан быть полностью определён (оба счёта каждого правила).
- `each: '<табличное поле>'` — проводка на каждую строку табличной части.
- `amount`, `qty`, `qty2`, аналитики — выражения безопасного мини-языка ([`sources/data/expr.js`](/sources/data/expr.js/~/handlers/pages/form/)), не JS.

### Р3. Табличные части

Тип поля `Table` с вложенными `FIELDS`, включая `Link`. Строки хранятся в теле объекта.

### Р4. Нормативы и ставки — через счета

Справочник «Виды нормативов», счёт «Нормы» с аналитиками «вид норматива» и «объект», операция «Установка норматива», которая проводит разницу между старым и новым значением. В выражениях `norm('Вид', объект?)` — сальдо на дату операции. История нормативов — сам журнал. Фиксированный норматив — константа, расчётный — выражение. Ставки налогов и взносов — тоже нормативы.

### Р5. Автоаналитики проводки

У каждой проводки есть автор, рабочее место, подразделение, операция и класс операции — отдельные колонки с индексами.

### Р6. Общие классы

Классы справочников, операций и счетов общие (`/DATA`). Данные разных подразделений различаются аналитикой подразделения. Собственные классы-наследники у подразделений — позже.

### Р7. Ссылки и время

- `Link` хранит `id` объекта и его класс. Версии объекта имеют `valid_from`, поэтому объект читается «как был на дату», и ссылка из операции показывается в состоянии на дату операции. Снимки (копии полей) не нужны.
- Реальные справочники наследуются: «Субъекты» → «Юр. лица», «Физ. лица». Запрос к родителю возвращает объекты потомков.
- Виртуальные справочники («Клиенты»): состав на дату — по сальдо счёта. Собственные поля — записи-расширения (`ext_of`) с версиями.
- Поле может ссылаться на виртуальный справочник, сохраняется id реального объекта. Выбор без поиска показывает только состав на дату операции (например, все работающие сотрудники для ведомости). При поиске к участникам примешиваются подходящие объекты реального справочника, выбор можно расширить на весь справочник, а если ничего не нашлось — создать объект и сослаться на него. Проведение состав не проверяет: участником объект делает сама операция (первая продажа делает покупателя клиентом).

### Р8. Видимость — `scope` на ссылке рабочего места

| `scope` | Видно |
|---|---|
| `own` | свои объекты |
| `place` | объекты своего места |
| `unit` | объекты подразделения и вложенных |
| `all` | всё |

По умолчанию: справочники — `all`, операции и счета — `unit`. BOSS видит своё поддерево на чтение, ADMIN — всё. Реализация — фильтр по колонке подразделения против списка потомков из `class_tree`.

- Ссылка: `{ id: '/ПУТЬ', access: 'read'|'write', scope? }` в `LINKS` места или общих `LINKS` подразделения. Подразделение `unit` — cid структуры, место `place` — путь в дереве `ROLES` подразделения (`'sales/junior'`), смысл имеет только вместе с подразделением.
- Вышестоящее место видит ссылки вложенных на чтение: `unit`/`all` — как есть, `own`/`place` — объекты вложенного места. BOSS подразделения — подразделение с вложенными (`all` остаётся `all`), ADMIN подразделения — всё по его ссылкам. Назначение в самом классе данных — всё.
- Ссылка на класс вызова или его предка открывает поддерево класса; ссылка ниже — только свою ветку: сводный отчёт предка (журнал, ОСВ, выборка) строится по видимым веткам; у ОСВ и карточки ветка счетов проверяется по счёту своей стороны, у журнала — по любой стороне.
- Состав виртуального справочника — по проводкам, видимым через него; поиск по реестру-источнику и чтение его объектов — по видимости самого реестра (новый покупатель находится, даже если он клиент другого подразделения).
- Создание: подразделение и место берутся из мест записи пользователя (ссылки на запись к листу); указанные клиентом проверяются; мест несколько — их нужно указать.

### Р9. Количество и единицы измерения

Проводка хранит `qty` в базовой единице номенклатуры, а также количество и единицу документа для показа. У номенклатуры есть табличная часть «Единицы» (единица, коэффициент к базовой, цена). `qty2` — второе измерение (масса топлива при учёте в литрах через плотность партии).

### Р10. Всё, что не проведено, не существует

Отчёты и состояния объектов строятся только по зарегистрированным операциям. Черновик — не факт.

### Р11. Типовая конфигурация и печатные формы

Шаблоны — файлы в метапапке класса операции (`$operation/print/*.html|docx`), наследуются вниз через `~`. Шаблон «Платёжное поручение» у «Платежей с р/с» применим ко всем дочерним платежам.

### Р12. Единый журнал

Журнал один. «Бухгалтерские», «управленческие» и другие счета различаются только кодом, названием и ссылками рабочих мест: бухгалтер видит бухгалтерские. Счета адресуются стабильным `cid`, а не путём.

### Р13. Хранилище

Одна БД `.data/work.db` — источник истины, обязательна в резервной копии. RAG и ленты — отдельно в `.index/work.db`, их можно пересобрать. `cid` класса — поле `CID` собственного слоя `class.js`; перенос и переименование папки не рвут данные.

### Р14. Поставка

Кроссплатформенно: служба Windows и systemd на Linux. ИИ — любой провайдер: локальный llama.cpp/vLLM, сервер в контуре или облако. Система всегда внутри локальной сети организации. Комплект «под ключ» для малых предприятий — мини-ПК с локальной моделью.

### Р15. Орг-навигация

Пользователь может работать в нескольких подразделениях и местах. Навигатор показывает дерево «мои подразделения и места», а руководитель проваливается в подчинённые подразделения (сводный вид поддерева). Контекст (подразделение, место) определяет меню и фильтры.

## 3. Схема БД

```sql
classes (cid PK, path, parent, type, label, own JSON, hash)     -- кэш class.js
class_tree (ancestor, descendant, depth)                        -- замыкание иерархии

objects (id PK, cid, status, time, author, place, unit, ext_of, version, created, updated, body JSON)
object_versions (id, version, valid_from, author, status, body)
refs (obj_id, field, row, ref_id, ref_cid)                      -- обратные ссылки
objects_fts (FTS5)                                              -- полнотекстовый поиск

entries (id PK, op_id, op_version, op_cid, rule, row, time, debit_cid, credit_cid,
         amount /*копейки*/, qty, qty2, doc_qty, doc_unit, author, place, unit, storno, created)
entry_analytics (entry_id, side 'D'|'C', slot, ref_id, ref_cid)

settings (key, value)                                           -- дата закрытия периода и т. п.
```

Итог по родительскому классу (счёт со всеми субсчетами, промежуточный класс операций, подразделение со всеми вложенными) — запрос по потомкам из `class_tree`. Физически собирать итоги вверх не нужно: правила спускаются по дереву вниз, данные поднимаются вверх запросом.

## 4. Первая демо-конфигурация

Оптовый дистрибьютор машинных и промышленных масел и топлива:
- **справочники:** субъекты, номенклатура с единицами (л, кг, т, бочка, канистра, IBC), склады и резервуары, партии с плотностью, договоры, транспорт, виды нормативов;
- **операции:** платежи и поступления, поступление товара, перемещение, фасовка, реализация, возврат, доставка, естественная убыль, инвентаризация, зарплата, кадры, коммуникации, установка норматива;
- **места:** директор, продажи, закупки, склад, логистика, бухгалтерия.
