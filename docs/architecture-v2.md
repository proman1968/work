# Архитектура WORK: учётная система и организационная модель (ODANT → WORK)

Дата фиксации: 26.10.2026. Статус: **утверждена пользователем**.

Дополняет [`whitepaper.md`](/whitepaper.md/~/handlers/pages/form/) и определяет устройство доменов, модулей, классов данных, явной двойной записи, двухэтапных аналитик и экранных форм в веб-проводнике WORK.

---

## 1. Главный принцип: модель ODANT + движок Node.js (`node:sqlite`)

В классическом ODANT скорость и гибкость обеспечивали два фактора:
1. **Объектно-иерархическая модель данных:** разделение на домены, модули и классы, трёхосевое наследование, хранение объектов в своих классах, **явная двойная запись** (проводки пишутся в два отдельных класса счетов — Дебета и Кредита, каждый со своими аналитиками), двухэтапная фильтрация по аналитикам и агрегация итогов снизу вверх по дереву классов.
2. **Быстрый C++ XML/XQuery-движок** по файловым пакетам и индексам.

В WORK (Node.js + JSON + Web):
- **Прикладная и архитектурная модель ODANT сохраняется 1-в-1** (никаких искусственных `CID`, никакой свалки всех счетов в одну плоскую реляционную таблицу в обход классов, никакого второго интерфейса вне проводника ODA).
- **Физическим ускорителем пакетов и индексов под капотом** внутри каждой организации (`$base`) выступает встроенный в Node.js Си-движок `node:sqlite` (как быстрый локальный JSON-индекс и транзакционное хранилище объектов классов этой базы взамен C++ XQuery), связанный с файловой структурой классов и логами (`data.logs`).

## 2. Организационная модель: Домены, Модули, Организации, Рабочие места

### 2.1. Иерархия верхнего уровня и жёсткие ограничения вложенности типов
Внутри любого элемента дерева всегда могут находиться обычные файлы (`$file`) и папки (`$folder`). Для типизированных узлов действует строгая иерархия вложенности (`allowed_child_types` и объявления в `<метапапка>/$folder/$class/*`):
- **`$class` (Абстрактная развилка в `/$server/$folder/$class`):** базовый прототип для всех типизированных узлов. Сам `$class` является абстрактным и **нигде в дереве не создаётся** как экземпляр.
- **`$server` (Корень WORK):** внутри `$server` (кроме `$file` и `$folder`) могут находиться **только домены (`$domain`)** и системные разделы верхнего уровня.
- **`$domain` (Домен / Раздел хранения структур):** место, где хранятся другие структуры:
  - `/ORGANIZATIONS` (`$domain`) — контейнер организаций, внутри которого могут создаваться только **`$base`** (и группирующие `$domain`);
  - `/MODULES` (`$domain`) — контейнер модулей, внутри которого могут создаваться только **`$module`** (и группирующие `$domain`);
  - `/DATA` (`$domain`) — контейнер прикладных разделов данных (`$catalog`, `$struct`, `$operation`, `$register`).
- **`$module` (Модули в `/MODULES`):** автономные функциональные пакеты (единицы поставки и обмена функционалом в экосистеме). Внутри модуля допускаются `$domain`, `$module`, `$catalog`, `$struct`, `$operation`, `$register`.
  - Сам модуль устанавливается один раз в корень системы (`/MODULES/<Модуль>`).
  - В конкретной организации (`$base`) в домене `MODULES` подключаются нужные ей модули.
- **`$base` (Организация / Проект внутри `/ORGANIZATIONS`):**
  - Внутри `$base` допускаются только структурные подразделения **`$structure`**, дочерние **`$base`** (филиалы), **`$domain`** и **`$module`**.
  - **Полная изоляция данных:** у каждой `$base` — **своя собственная БД** внутри её папки (`<Организация>/$base/#system/work.db`). Данные разных `$base` никогда не смешиваются.
- **`$structure` (Подразделение):** внутри `$structure` могут находиться только вложенные подразделения **`$structure`**.
- **Прикладные классы данных:**
  - внутри **`$catalog`** → только `$catalog` и `$virtual` (при соблюдении инварианта листа);
  - внутри **`$virtual`** → только дочерние `$virtual` (специализированные виртуальные выборки, например `Сотрудники → В отпуске`, наследующие `SOURCE` и `OVERLAY` родительского виртуального справочника);
  - внутри **`$struct`** → только `$struct`;
  - внутри **`$operation`** → только `$operation` (при соблюдении инварианта листа);
  - внутри **`$register`** → только `$register` и `$account`;
  - внутри **`$account`** → только `$account` (субсчета, при соблюдении инварианта листа).

### 2.2. Подразделения (`$structure`) vs Рабочие места
В WORK понятия подразделения и рабочего места разделены по назначению:
- **Подразделение (`$structure`):** точка коллаборации и управления. Здесь живут произвольные файлы, чаты, задачи, почта, лента событий (`logs`), и здесь назначаются `ADMIN` и `BOSS` подразделения.
- **Рабочее место (внутри подразделения):** должностная точка работы с учётными данными («молотилка данных»). Сюда назначаются сотрудники-исполнители и привязываются ссылки (`LINKS`) на классы данных (включая классы внутри подключённых модулей `$base/MODULES/<Модуль>/...`). Сотрудник рабочего места автоматически входит в состав своего подразделения.
- **Права на ссылках в рабочем месте:** только два понятных режима — **`read` (чтение)** и **`write` (изменение)**. Права `ADMIN` остаются только на уровне структурных подразделений (`$structure` / `$base`).
- **Видимость дерева проводника:**
  - `ADMIN` базы видит полное дерево `$base` (включая `MODULES` и все классы данных).
  - Конечный пользователь видит только цепочку до своих рабочих мест и прилинкованные к его рабочему месту классы (с подчёркнутыми названиями-ссылками прямо внутри узла рабочего места).

## 3. Трёхосевое наследование классов

Никаких искусственных `CID` (`cat.items`, `acc.41`) не используется. Идентификатор класса — имя его папки, а адрес — полный путь в дереве.

Любой класс собирает свои метаданные (`FIELDS`, `STATIC`, `POSTINGS`, `OVERLAY`, методы и формы) по трём осям в следующем порядке приоритета (от базового к приоритетному):

```text
1. Types (миксины)  →  2. Ancestor (предок в корне/модуле)  →  3. Parent (родитель в дереве)  →  4. Сам класс
```

1. **`Types` (расширение по типам / миксины):** в метаданных класса может быть задан список `types: ['/путь/к/классу', ...]`, примешивающий к классу поля, методы и обработчики указанных классов (например, миксин координат и вида карты).
2. **`Ancestor` (одноимённый предок в корневом модуле или вышестоящей базе):** класс внутри организации (`Организации / Мое предприятие / MODULES / Register / Операции / Отгрузка`) автоматически наследует метаданные от класса с тем же относительным путём в корне (`/MODULES / Register / Операции / Отгрузка`). В базе создаются и донастраиваются только нужные ей классы.
3. **`Parent` (родитель в текущем дереве):** наследование сверху вниз по цепочке однотипных классов (`Операции` → `Отгрузка` → `Покупателю`).

## 4. Типы классов данных, Структуры и Табличные поля

Все домены и прикладные типы являются наследниками `$class`:
- **`$catalog` — Справочник:**
  - Если у класса есть дочерние классы (`Адресаты` → `Юр. лица`, `Физ. лица`, `ИП`) — он является группой: своих объектов не создаёт, но при открытии показывает все объекты дочерних классов, и на него можно ссылаться как на полиморфный тип «любой Адресат».
  - Если класс конечный (лист) — в нём создаются объекты.
  - Отдельный дублирующий тип `$registry` не нужен — везде используется `$catalog`.
- **`$virtual` — Виртуальный справочник («Клиенты», «Поставщики», «Сотрудники», «В отпуске»):**
  - Опирается на базовый `$catalog` и счёт `$account` (`SOURCE: { catalog, account, slot, mode }`).
  - Режим отбора (`mode`) настраивается:
    - `'turnover'` (по обороту) — все объекты, которые хотя бы раз участвовали в движениях по счёту (например, «Клиенты» на счёте 62 не исчезают после оплаты долга в ноль);
    - `'balance'` (по ненулевому/положительному остатку на дату) — только активные на выбранную дату объекты (например, «Сотрудники в штате», «Сотрудники в отпуске»).
  - Собственные дополнительные поля виртуального справочника задаются в `OVERLAY` и хранятся как расширения (`ext_of`) с историей версий.
- **`$struct` — Структура (составной тип поля):**
  - Описывает набор полей составного реквизита («Паспорт», «Адрес», «Строка накладной», «Единица измерения»). Собственных отдельных объектов в БД не имеет.
  - Когда поле другого класса ссылается на `$struct`:
    - при `table: false` (по умолчанию) — значение поля является вложенным объектом `{ Серия, Номер, Адрес: { ... } }` (поддерживается любая глубина вложенности структур);
    - при **`table: true` (признак «Табличное» у поля)** — значение поля является массивом таких структур `[{...}, {...}]` (табличная часть). Отдельного типа поля `Table` не требуется: табличность — это булев признак `table: true` любого поля.

## 5. Операции (`$operation`), Счета (`$account`) и Явная двойная запись

### 5.1. Честная история (без `delete` и переписывания задним числом)
- WORK фиксирует реальный рабочий трек во времени, а не «причёсанный» задним числом результат.
- Версии объектов справочников сохраняются во времени (`valid_from`), поэтому операция на прошлую дату видит реквизиты объектов в том состоянии, в котором они были на дату операции.
- Проведённая операция неизменяема: любое её исправление или отмена выполняется только через **сторно** прежних проводок и запись новых проводок, оставляя полный след в истории.
- Каждая регистрация/исправление/отмена операции записывает факт в `data.logs` подразделения и автора (единый контур с лентой событий WORK).

### 5.2. Явная двойная запись по классам счетов (`$account`)
- Журнал (`$register`) в организации один, а каждый счёт и субсчёт — это отдельный класс `$account`, поэтому права в рабочих местах выдаются точечно на конкретные счета или ветки счетов.
- Правила проводок (`POSTINGS`) задаются в метаданных классов операций (`$operation`) и наследуются сверху вниз по дереву операций (полный набор правил определён в конечных операциях-листьях).
- **Явная двойная запись:** при проведении операции каждое сработавшее правило создаёт **две отдельные записи в двух разных классах счетов (`$account`)**:
  1. **Запись в классе счёта Дебета** (`account_path = Дт`, `corr_account = Кт`, `debit = сумма`, `credit = 0`, `qty_in = кол-во`, `qty_out = 0`, плюс значения **только тех аналитик**, которые объявлены на счёте Дебета);
  2. **Запись в классе счёта Кредита** (`account_path = Кт`, `corr_account = Дт`, `debit = 0`, `credit = сумма`, `qty_in = 0`, `qty_out = кол-во`, плюс значения **только тех аналитик**, которые объявлены на счёте Кредита).
- Обе записи связаны общим ключом проводки (`entry`) и ссылкой на операцию (`op_id`, `op_path`).
- Агрегаты оборотов и сальдо каждого счёта поднимаются вверх по иерархии субсчетов к родительским счетам и всему журналу (`$register`).

### 5.3. Двухэтапный механизм аналитик (субаналитики)
1. На счёте (`$account`) аналитики объявляются как поля-ссылки (`analytic: true`) на классы справочников (чаще всего виртуальных: «Сотрудники», «Клиенты», «Поставщики», «Номенклатура»).
2. В записи движения счёта хранится только `id` объекта аналитики.
3. При построении отчёта по счёту все поля справочника-аналитики (и базового `$catalog`, и расширения `OVERLAY` у `$virtual`) доступны как **субаналитики**:
   - **Шаг 1:** фильтр отбирает объекты справочника по любым их полям (например, `Должность = Водитель`, `Возраст > 30`, `Менеджер = Иванов`) и получает список `id`;
   - **Шаг 2:** по полученному списку `id` фильтруются (или группируются) записи движений счёта и вычисляются сальдо и обороты.
   Это полностью решает проблему декартова произведения аналитик на счетах.

## 6. Четырёхшаговый интерфейс Журнала и Счетов в проводнике ODA

Единственный пользовательский интерфейс — штатные вкладки проводника ODA (`work-form`). Во всех учётных формах сверху располагается единая шкала выбора периода **`oda-packets`** (годы, кварталы, месяцы, произвольный период, весь период).

1. **Экран 1 — Общая ОСВ Журнала (`$register` → `sheet`):**
   - Дерево всех счетов и субсчетов: `На начало (Дт / Кт)` | `За период (Дт / Кт)` | `На конец (Дт / Кт)` и строка общих итогов баланса внизу.
   - Внизу кнопки перехода от выбранного счёта: **Обороты | Анализ | Проводки**.

2. **Экран 2 — Анализ счёта (`$account` → `analysis`):**
   - ОСВ внутри выбранного счёта в разрезе его аналитик.
   - **Левая панель:** список аналитик счёта (с кнопками перестановки порядка иерархии `↑↓` и фильтром по значениям и субаналитикам) + переключатель **ЗНАЧЕНИЯ: Сумма / Количество**.
   - **Правая таблица:** строки по объектам аналитики (`На начало` | `За период` | `На конец`), строка быстрого фильтра под шапкой, развёрнутые итоги внизу. Переход по кнопке **Обороты** на выбранном объекте аналитики.

3. **Экран 3 — Обороты счёта (`$account` → `turnovers`, двухпанельный master-detail):**
   - **Крайняя левая панель — `ГРУППИРОВАТЬ`:** *Нет | Дни | Недели | Месяцы | Кварталы | Годы | Операции | Счета | Все*.
   - **Левая таблица:** `На начало`, строки периодов/групп (`Дебет | Кредит | Сальдо | Оборот`), `На конец`.
   - **Правая таблица:** список операций (первичных документов) выбранного слева периода с указанием вида операции, корреспондирующего счёта (`на сч. ...` / `со сч. ...`), сумм Дебета/Кредита и кнопками открытия **Проводки** и **Документа**.

4. **Экран 4 — Карточка проводки (сборный микро-отчёт):**
   - Собирается по ключу `entry` из записей класса счёта Дебета и класса счёта Кредита:
   - Вверху — шапка операции (дата, сумма, операция, ссылка на документ).
   - Внизу — две симметричные половины: слева **Дебет** (счёт, его аналитики и сумма/кол-во), справа **Кредит** (счёт, его аналитики и сумма/кол-во).
