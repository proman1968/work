# Хранилище WORK

## 1. Что это

Единая модель хранения WORK: классы, файлы, данные, индексы и логи. Технически — раскладка метапапки класса и правила движка (`sources/server/`). Прикладно — основа учётной системы (справочники, операции, журнал).

## 2. Зачем это нужно

Одно хранилище вместо разрозненных баз: документы, типизированные объекты, агрегаты и факты сходятся в одну точку. ИИ-управляющий понимает состояние организации через файлы и логи. Двойная запись и отчёты строятся поверх тех же механизмов, а не отдельным движком.

## 3. Как это работает

### 3.1. Метаданные класса (`class.js`)

```js
METADATA: {
  STATIC:   [...],  // свойства самого класса (настройки: baseUrl, tariff, …)
  FIELDS:   [...],  // поля объектов .data этого класса (наследуются, слияние по id)
  INDEXES:  [...],  // определения индексов
  POSTINGS: [...],  // правила разноски ($operation)
}
LINKS: [ { id: '/DATA/REGISTER/50', access: 'read' }, … ]  // только $group (рабочее место)
```

`STATIC` — свойства самого класса. `FIELDS` — схема объектов. Раньше одно имя `FIELDS` использовалось в двух смыслах; теперь смыслы разделены, как в предыдущей версии ODANT (`METADATA`/`STATIC`).

Однотипное наследование идёт только через `$distr_folder`: при `save()` содержимое `FIELDS`/`INDEXES`/`POSTINGS` автоматически попадает и в свой `class.js`, и в наследуемую потомками часть (кроме явного `to_inherit: false`). `STATIC` не наследуется. Поэтому субсчета видят аналитику и индексы счёта, а собственные настройки (`label`, тарифы, ключи) — нет. Путь distributive повторяет цепочку типов из `$server` (`$class/$structure/$base`, а не `$class/$base`): тесты-песочницы обязаны копировать и `$server`-звено цепочки, иначе тип резолвится короче и файл не подхватывается.

### 3.2. Раскладка метапапки

```text
<Класс>/$<тип>/
├─ class.js, readme.md            SYSTEM  (правит ADMIN)
├─ #security #secret #system      SECRET
├─ $folder/…                      наследуемое для потомков
├─ logs/YYYY-MM-DD/*.logs         LOGS    факты
├─ <ROLE>/                        ZONE    документы ролей — только $structure
├─ DATA/YYYY-MM-DD/{t}.{uid}.data         объекты — только лист прикладного типа
│        .{t}.{uid}.data/history|files    версии, вложения
└─ INDEX/<id>/…                           агрегаты — все уровни прикладного типа
```

### 3.3. Файлы и данные

- `$data` (`.data`, JSON) — единственный тип данных. Схема — `METADATA.FIELDS` класса-владельца.
- `$eml`, `$ics`, `$call`, `$task` — обычные типы файлов в зонах ролей структурных классов. Переход: пока остаются в `$data` (зоны ролей сохранены), вынос в `$file/*` — следующий шаг.
- `$logs` — системный формат области `logs`, к данным не относится.
- Каждое действие = артефакт + факт в логе. Правка объекта пишет новую версию, прежняя уходит в `history`; удаление ставит отметку `deleted`. Проводки неизменяемы: отмена — сторно или замена.

### 3.4. Сбор снизу вверх (внутри одного типа)

`DATA` лежит только в листе. Запрос к промежуточному классу возвращает объекты всего поддерева того же типа. `INDEX` листа обновляется дельтами, дельта поднимается к предкам того же типа и всегда пересобирается из `DATA`. На границе типов (`$register` → `$account`) ничего не хранится: контейнер опрашивает корни дочернего типа.

### 3.5. Доступ: роль в группе и доступ ссылки

Рабочее место — это `$group`. Ссылка из `LINKS` распространяется на всё поддерево класса и открывает его канонический путь. Роль пользователя в прикладном классе — это его роль в группе со ссылкой (`read` — чтение, `write` — чтение плюс создание и правка объектов через API класса). `ADMIN` дополнительно правит структуру и код. В `DATA` пишет только API класса; `post` создаёт проводки под системной сессией.

### 3.6. Учёт поверх хранилища

`CATALOGS` — справочники. `OPERATIONS` — `FIELDS` и `POSTINGS`; `post`/`unpost` создают или сторнируют 2×N записей в листьях-счетах и обновляют их `INDEX`. `REGISTER` — базовые поля проводки в типе `$account`, аналитики — поля `Link` с флагом `analytic`; обороты и сальдо читаются из `INDEX` на любом уровне.

## 4. Из чего это состоит

- `sources/server/class.js` — `METADATA` (дефолт `FIELDS`/`STATIC`), `save_file`, API данных
- `sources/server/folder.js` — `getFolderToSaveFile`, наследование `~`, слияние слоёв
- `sources/server/file.js` — `save_to_history`, `save_to_log`, триггеры `on_save`
- `sources/server/logs.js` — факты, ленты, `feed`
- `sources/server/access/policy.js` — области `SYSTEM`/`ZONE`/`DATA`/`INDEX`/`LOGS`/`SECRET`
- `sources/modules/rag/` — индексация объектов, классов, логов; `query_objects`
- `oda/components/layouts/editor-form/editor-form.js` — формы по `STATIC` (настройки) и `FIELDS` (объекты)
- `DATA/` — класс «Данные»: учёт целиком; `DATA/REGISTER/` — журнал (`$register`) и счета (`$account`)
- `DATA/OPERATIONS/` — операции (`$operation`), `DATA/CATALOGS/` — справочники (`$catalog`)
