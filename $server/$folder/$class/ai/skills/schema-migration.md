# Безопасная перестройка и миграция структуры

1. **Обязательная разведка до любых правок:**
   - Запусти `inspect_class_tree` на целевом классе (и при изменении/удалении поля или переносе передай `simulate`: `{ remove_field }`, `{ rename_field: { from, to } }`, `{ change_type: { field, to } }`, `{ move_to }` или `{ delete: true }`).
   - Зафиксируй:
     - число объектов в `work.db` (особенно `registered` операций и записей проводок `entries`);
     - все входящие ссылки (`Link`, `Struct`, `POSTINGS`, `SOURCE`, `types`, `#security.ROLES[].LINKS`);
     - конфликты 3-осевого наследования (`Types → Ancestor → Parent → Self`).
2. **Блокирующие правила (тихая ломка запрещена):**
   - Нельзя удалять или несовместимо менять тип поля (`String` → `Link`, `Number` → `Date`), если в `work.db` есть непустые значения без плана миграции.
   - Нельзя молча удалять класс с объектами, проводками или входящими ссылками (`delete_class` с `dry_run=true` покажет блокеры).
   - **Проведённые учётные операции (`registered`) не переписываются задним числом** — если изменение ломает смысл старых документов, создаётся новый класс/версия или исправление оформляется через сторно.
3. **План миграции (показывается человеку до правок):**
   - Шаг 1: резервная оценка и заморозка/подготовка новых полей (`update_class` — добавить новое поле как необязательное).
   - Шаг 2: перенос/преобразование значений существующих объектов в `work.db` (либо при переносе класса — `move_class` с `update_refs=true`).
   - Шаг 3: проверка `inspect_class_tree` + `find_objects` после переноса.
   - Шаг 4: скрытие/удаление старого поля (`{ id, removed: true }` или `{ id, delete_own: true }`) либо `delete_class` после подтверждения чистоты.
4. **Контрольная проверка после миграции:**
   - Вызови `inspect_class_tree` на родительском узле (дерево, наследование, `checkSchema`, `work.db`, `ROLES`) и убедись в отсутствии ошибок.
