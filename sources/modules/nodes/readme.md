# sources/modules/nodes/ — сеть WORK

Серверы WORK образуют сеть: каждый знает набор узлов (реестр `/NODES`), которые могут
взаимодействовать с ним как субъекты, и сам обращается к ним как к хостам.

## Модель взаимного доступа

Пример: мы закупаем у поставщика SRV.

| Где | Что |
|---|---|
| у нас `/NODES/SRV` | локальный класс узла SRV; в его `ROLES` — роли, объявленные на SRV (из карточки узла); в `#security` мы назначаем **наших** пользователей на роли SRV: `CUSTOMERS: [Иванов]` — Иванов наш представитель по закупкам у SRV |
| у SRV `/NODES/<мы>` | наш сервер в реестре SRV (закреплённый ключ) |
| у SRV «Продажи» | наш сервер как субъект (его id) назначен на роль: `CUSTOMERS: ['<id нашего сервера>']` |

Иванов действует на SRV так: `/NODES/SRV?remote&as=CUSTOMER&path=/Продажи/...&method=...`
(POST, из-под своей сессии). Наш сервер проверяет, что Иванов назначен у нас на `CUSTOMER`
в `/NODES/SRV`, и отправляет SRV запрос, подписанный ключом сервера, с представителем `Иванов`
и заявленной ролью `CUSTOMER`. SRV проверяет подпись закреплённым ключом и работает с субъектом
«узел <мы> в роли CUSTOMER»: права — только роли `CUSTOMER` там, где SRV назначил наш сервер.
Записи в логах SRV: `sender` = id нашего сервера, `actor` = `Иванов@<наш id>`; лента отношений
пишется в класс нашего узла в реестре SRV.

Отозвать доступ может любая сторона: убрать узел из реестра, снять назначение, снять представителя.

## Файлы

| Файл | Роль |
|---|---|
| `identity.js` | ключ сервера Ed25519 (`#system/node-key.json`), карточка `/.well-known/work-node`: id, адрес, ключ, отпечаток, каталог ролей (кроме ролей только для пользователей), объявленные соседи |
| `signing.js` | каноническая строка подписи, заголовки `Work-*`, одноразовость nonce |
| `outbound.js` | `nodeFetch(node, {path, method, params, post, actor, roles})` — подписанный запрос к узлу |
| `inbound.js` | `verifyNodeRequest(request)` — проверка входящего запроса → эфемерная сессия субъекта-узла |
| `registry.js` | реестр: список узлов, карточка по адресу, добавление с закреплением ключа, обновление, граф сети |

## Протокол `work-node/1`

Подписывается (Ed25519) строка из строк: `work-node/1`, метод, путь с запросом, адресат (id сервера-получателя),
`Work-Date`, `Work-Nonce`, `Work-Node` (отправитель), `Work-Actor`, `Work-Roles`, `Work-Digest` (SHA-256 тела, base64).
Получатель проверяет: узел в реестре со статусом `active`, адресат — он сам, время ±5 минут, nonce не повторялся,
хеш тела, подпись закреплённым ключом.

## Реестр и визуализация

- Добавление (ADMIN): `/NODES?node_add` с `origin` → ответ с отпечатком ключа узла; после сверки с администратором
  узла — повторный вызов с `fingerprint` создаёт класс узла (ключ закрепляется).
- `/NODES/<узел>?node_refresh` (ADMIN) — обновить карточку: роли узла, назначения нашего сервера у него (`node_grants`).
  Смена ключа не принимается молча: статус `key_changed`, узел блокируется.
- `announce: true` — узел публикуется в нашей карточке (`peers`): так строится реестр сети.
- `/NODES?network_graph&depth=2` — граф: мы, узлы реестра, их объявленные соседи; вид `Сеть` на `/NODES`
  (`NODES/$node/handlers/pages/form/network`).

## Ограничения текущей версии

- Удалённое дерево пока не монтируется в UI как часть нашего: действия — через `remote`.
- `node_grants` берёт назначения из индекса RAG (карточки классов); без индекса список пуст.
- Лично назначить пользователя чужого сервера (`uid@узел`) нельзя — только узел целиком через его представителей.
