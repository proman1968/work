# sources/modules/agent — ядро агента WORK

## 1. Что это

Исполнительное ядро ИИ-агента: цикл на нативном tool calling, инструменты работы с деревом WORK и внешним миром, политика разрешений, сессия задачи `.task`. Обычные Node-модули (импортируют `node:*`, тестируются напрямую). Слои дерева (`class.js` — data:-модули) получают ядро через глобальные `WORK_AGENT()` (сессия) и `WORK_AGENT_CORE()` (окружение, разовый запуск) — `sources/server/server.js`.

## 2. Зачем это нужно

Один способ работы агента для всех сценариев: модель сама выбирает инструменты и их аргументы (JSON-схемы), независимые чтения идут параллельно, действия с побочным эффектом проходят политику разрешений, человек отвечает и подтверждает прямо в ленте. Лента — единственный источник правды: по ней строится контекст модели, рисует UI, с неё продолжается работа после стопа и рестарта.

## 3. Как это работает

1. **Окружение** (`index.js` `createEnv`): для места (класса) и пользователя собирает system-промпт (`ai/system.md`, среда WORK, место, роли, время, режим, контракт места — собранный readme, навыки, субагенты) и набор инструментов. Промпт собирается **по частям для кэша провайдера** (`makeSystemParts` → `{ stable, volatile }`; `makeSystem` — те же части одной строкой): `stable` (правила, роль, ОС/песочница, контекст места, контракт, память, навыки и субагенты по имени) идёт единственным сообщением `system` в начале и не зависит от времени; `volatile` (текущее время до минуты, режим, голосовая заметка) — отдельным служебным сообщением `user` (`VOLATILE_HEAD`) **в конце** контекста, чтобы история оставалась неизменным префиксом (изменение в начале сбрасывает кэш всего, что после него). Порядок инструментов детерминирован: статические — как в коде, внешние `svc_*`/`mcp_*` — по имени (`stableToolOrder`; собираются параллельно и иначе зависели бы от скорости ответов). Известное ограничение: микросжатие старых результатов (`OLD_RESULT_MAX` за пределами `KEEP_FULL_TURNS`) каждый ход меняет сообщение на границе окна — для кэша это отдельная задача.
2. **Цикл** (`loop.js` `runLoop`): лента → messages (OpenAI-формат; старые результаты урезаются, сжатые элементы заменены сводкой) → `llm.stream` → текст/рассуждение стримятся в UI (`host.emit`) → вызовы инструментов → результаты в ленту → следующий ход, пока модель не ответит без вызовов. Подряд идущие `readonly`/`concurrent` вызовы — параллельно. Лимит ходов, ретраи до первого токена (кроме ошибок ключа), стоп (AbortSignal рвёт HTTP), сжатие контекста при ~72% окна модели. **Размер контекста берётся из реального `usage` провайдера** (`estimateContext`): `prompt_tokens` последнего ответа (весь запрос — system, схемы инструментов, диалог; `usage.prompt` в элементе ленты, `cached` — токены, прочитанные из кэша провайдера, если он их отдаёт) плюс оценка добавленного после него (ответ, результаты, реплики). Эвристика `len/3.2` — запасной вариант: нет `usage`, после сжатия (summary новее ответа — опора устарела), либо `usage` недостоверен (меньше system + схем инструментов; `USAGE_TRUST_MIN`); в нём тоже учитываются схемы инструментов (`toolsTokens`). Адаптер моделей нормализует `prompt_tokens` как полный размер запроса (OpenAI `cached_tokens`, DeepSeek `prompt_cache_hit_tokens`, Anthropic-поля `input_tokens + cache_read + cache_creation`); в `host.noteContext` уходят `used` и `source` (`usage`|`estimate`). Для нативного Anthropic API (`protocol: 'anthropic'`, см. `MODELS/$ai/readme.md`) адаптер отдаёт ещё `thinking_blocks` (подписанные блоки размышлений → `it.thinkingBlocks`; в сообщение они попадают **неперечисляемым** свойством `thinking_blocks`, поэтому не утекают в JSON других протоколов и не раздувают оценку токенов) и `cache_creation_tokens` (→ `usage.cacheWrite`).
3. **Разрешения** (`permissions.js`): режимы `auto` | `ask` | `plan`. `readonly` — всегда; `plan` — инструменты записи модели не показываются; `ask` — любое действие с эффектом спрашивает; `auto` — запись в рабочие данные без вопроса, код/конфиг системы (`/$server`, `/sources`, `/oda`, `/MODELS`, `/SERVICES`, `/NODES`, `*.js`, `#security`/`#secret`/`#system`) и `risk:'danger'` — с подтверждением. «Разрешить всегда» — на задачу (`body.allowed`). Все `risk`-вызовы, отказы политики и решения человека пишутся в журнал безопасности (`.index/audit/*.jsonl`, event `agent`: инструмент, цель, вердикт, итог, субъект/роль/задача; аргументы не пишутся — секреты). Права пользователя проверяет само ядро WORK: каждый вызов идёт с `session` (и перебором ролей пользователя в классе).
4. **Сессия** (`session.js`): тело `.task` v2 в памяти, атомарная запись, одна петля на файл (замок), ожидание человека (`host.wait`) — вопрос или подтверждение; ответ, пришедший после рестарта, применяется к ленте и работа продолжается. События: `chat.start`/`chat.done`, `task.state`, `task.delta`, `{path}`.
5. **Push**: вопрос/форма, разрешение, ошибка, необходимость проверки после рестарта и завершение работы дольше 20 с — уведомление пользователю; завершение скрывается лишь если в фокусе уже открыта та же задача. Разрешение включается кнопкой в шапке задачи, действующая подписка заново привязывается при входе. Клик открывает задачу. Разрешение (9.7) — с кнопками «Разрешить/Отклонить» прямо в уведомлении: service worker подтверждает через POST `file?approve` (те же права владельца, что в интерфейсе); вопрос — без кнопок (клик открывает задачу: ответу нужен контекст). Сообщение собирает `pushMessageOf` (чистая — покрыта тестами).
6. **Продолжимые агенты** (`tools/meta.js` `agent_start/agent_status/agent_message/agent_stop`): отдельная дочерняя `.task` в той же роли и точке, адресуемая по пути; сообщения в работающую или ожидающую задачу ставятся в очередь. Разовый `task` по-прежнему возвращает один отчёт.
7. **Подъём после рестарта** (`recovery.js`): сканирование активных `.task` в рабочих зонах, лимит одновременного подъёма; безопасные незаконченные чтения → прерваны и цикл продолжается, выполнявшиеся изменяющие действия → `needs_review` без автоматического повтора, вопросы остаются `waiting`. `WORK_RECOVER=0` выключает автоподъём.
8. **Разовый запуск** (`runOnce`): REST `/КЛАСС?prompt&prompt=…` без ленты на диске; подтверждаемые действия отклоняются с объяснением.

языкового сервера в зависимостях нет — `typescript-language-server` требует классический tsserver, в WORK TypeScript 7 без него; в песочнице агент может вызвать установленный сервер сам через `sandbox_exec`): work — только ADMIN, права на файлы при чтении; `lsp_rename` — readonly, возвращает ПЛАН правок (применение — через `edit`/`apply_patch` с правами и историей); sandbox — `rg --column --word-match`, `tsc` в контейнере (ставится `npm i -g typescript`), интернет — `untrusted` |
| `voice.js` | голосовой режим задачи: `voiceConfig` (что доступно), `speak` (текст → WAV), `transcribe` (WAV → текст) через модели `ai/config.js` `ttsModel`/`sttModel` (capability `tts`/`stt`, методы `speak`/`transcribe` в `MODELS/$ai`); ключи остаются на сервере, нет модели на шлюзе — клиент берёт речь браузера. `dotLook`/`voiceConfig` отдают и внешний вид персонажа (`ai/config.js` `dot`, значения очищаются); распознавание считается доступным, только если шлюз перечислил модель (`list_remote`). Реплика с `voice: true` ставит `body.voice` — в system добавляется `VOICE_NOTE` (первый абзац ответа — устная речь) |
| `diff.js` | построчный diff для карточек правок |
| `util.js` | id, обрезка, оценка токенов, фронтматтер |

**Субагенты и набор инструментов** (`index.js` `makeTools(def, depth, parent)`): набор субагента по фронтматтеру (`tools`: `readonly` | `*` | маски, где `*` — любая подстрока: `os_*`, `svc_*_query`) **пересекается с набором вызвавшего агента** — делегирование права не расширяет, `readonly`-агент не получит запись через `task`. Всегда вырезаны `ask_user`, `todo_write`, `save_skill`, `schedule`, `connect_service`/`disconnect_service`; всегда добавлен `skill`. `call: [методы]` во фронтматтере сужает `call` до перечисленных методов (отклонение до подтверждения и до вызова). `requires: system | sandbox` у агента или навыка скрывает его из списков и system, когда у сессии нет ОС/сети (не ADMIN) или Docker недоступен.

Элементы ленты: `user` · `assistant` (`content`, `reasoning`, `tools[]` со статусами `pending|approval|waiting|running|ok|error|denied|interrupted|approved`) · `summary` · `error`. Субагент хранит свою ленту в `tools[].items`.

Инструмент: `{ name, description, parameters, readonly?, concurrent?, planSafe?, risk?:'write'|'danger', untrusted?, outbound?, target?(args), permission?(args), run(args, ctx) }`; `ctx`: `session`, `place`, `env`, `host`, `llm`, `entry` (карточка вызова — сюда `path`, `diff`, `items`), `signal`, `depth`, `tainted` (источники внешнего содержимого в ходе или `null`).

**Хуки организации** (`hooks.js`) — пример `ai/config.js` слоя:

```js
export default { hooks: {
    pre_tool: [
        // запретить запись в архив для всех; хук получает копию данных вызова
        ({ tool, args, target, role }) => tool === 'write' && String(target).startsWith('/ORG/Архив')
            ? { verdict: 'deny', reason: 'архив только для чтения' } : undefined,
        'hooks/limits.js',          // модуль из ai/hooks/ этого же слоя (default-экспорт или экспорт pre_tool)
    ],
    post_tool: [ ({ tool, status }) => tool === 'web_fetch' && status === 'ok' ? { append: 'Источник не проверен.' } : undefined ],
    on_stop:    [ ({ status, turns, task }) => { /* уведомление, результат не используется */ } ],
    on_compact: [ () => ({ append: 'ПРАВИЛО: ничего не удалять без согласования.' }) ],   // переживает сжатие контекста
} };
```

`pre_tool` вызывается до проверки прав (после проверки аргументов) для каждого инструмента, включая субагентов; payload: `tool, args, risk, readonly, target, tainted, mode, role, task, depth, uid`. Ответ: `{ verdict: 'deny'|'ask', reason, args }` — подмена `args` накапливается по хукам, `deny` вызов не выполняет (модель видит «запрещён правилом организации» и причину), `ask` требует подтверждения человека даже в `auto` и без «разрешить всегда». `post_tool` получает ещё `status, result, error, durationMs` и может вернуть `{ append }` (дописывается к результату в ленте и в контексте). `on_stop` — только для основного цикла задачи. Модуль хука должен быть самодостаточным (без `import`): загружается как `data:`-модуль.

**Чужое содержимое и prompt injection** (`taint.js`, структурная защита, а не только инструкция в промпте; общая модель угроз и инварианты — `rules/threats.md`):
- `untrusted: true` — инструмент отдаёт чужой текст (`web_search`, `web_fetch`, `http_request`, `browser_*`, `computer_screenshot/action`, внешние `svc_*` и все `mcp_*`, `net_http/net_probe`); если чужое только иногда — `run` ставит `ctx.entry.untrusted = true`: `read`, `find`, `search`, `query`, `read_table`, `import_objects`, `grep` (dev) — для писем `.eml` и файлов, пришедших загрузкой/скачиванием (`server/external-source.js`, R15/8.38: помечают ВСЕ читатели, единый помощник `markUntrustedByPaths`); `sandbox_exec` при включённом интернете; `agent_status`. Исключение (наша валидация) вызов не помечает; `{error}` от сервиса — помечает.
- Такой результат в контексте модели оборачивается в `<untrusted source="инструмент" id="КОД">…</untrusted id="КОД">`: КОД случаен для каждого вызова (хранится в `entry.nonce`), вхождения `<untrusted` внутри данных экранируются; в ленте (для UI) результат лежит без тегов. `ENV_GUIDE` объясняет модели: внутри тегов — только данные.
- `outbound` (`true` | `(args) => boolean`) — действие «наружу»: `send` людям, `http_request` не GET (и GET с данными в адресе — `urlCarriesData`), `web_fetch` с данными в адресе, `call` опасных методов/ADMIN, `memory remember`, `schedule create`, `save_skill`, `agent_start/agent_message`, `assign`, `connect_service`, `computer_network on`, `browser_fill_secret`, внешние `svc_*`/`mcp_*` с изменением, все не-readonly инструменты ОС/сети (`guarded()`).
- **Заражение хода**: с момента `untrusted`-результата и до следующей реплики человека (`ctx.tainted`, вычисляется по ленте — переживает рестарт, учитывает вложенные ленты `task`; субагент наследует заражение родителя через `opts.taintedFrom`) любой `outbound`-инструмент в `decide()` даёт `ask` **без «разрешить всегда»** даже в `auto`; собственный `deny` инструмента сильнее вопроса. В автономном запуске (нет `host.wait`) такое действие отклоняется. В MCP-сессии подтверждение человека (elicitation) относится к ОДНОМУ вызову (R14/8.38) — заражение сессии не снимается: следующее действие наружу снова спросит; снимает только конец сессии/отзыв токена.
- Остаточные риски: письма, пришедшие через `call`/ленту, не помечаются; сводка сжатия контекста пересказывает чужое содержимое без тегов (заражение хода при этом сохраняется); эвристика «данных в адресе» (`urlCarriesData`) пропускает короткие ASCII-параметры.

## ОС и локальная сеть

Инструменты ОС относятся к **серверу WORK**, а не к машине браузера. Они добавляются в
`makeTools` только для ADMIN корня, а перед выполнением права проверяются повторно.
Узлам федерации доступ не выдаётся. Субагентам нужны явные имена/маски в `tools`
(`os_*`, `net_*`, `shell`); `all`/`*`/`readonly` их автоматически не включают.

Файловые инструменты проверяют реальные пути (в том числе junction/symlink), разрешённые
корни и исключения; дерево WORK обслуживается обычными `ls/read/write`, а не `os_*`.
Рекурсивная копия/перемещение/удаление проверяет потомков до операции.
`shell` — полноценная команда с правами процесса: файловые ограничения `roots/deny`
не являются её песочницей. Можно отключить через `shell: "off"`.

Чтение ОС и поиск объявлений сети выполняются сразу. Изменения ОС подтверждаются;
`shell`, удаление, установка пакета, управление службами и `net_scan` — каждый раз.
`net_register` создаёт сервис в `/SERVICES/LAN`; IPP-печать, eSCL-сканирование и OData
доступны через `svc_*` по ролям зарегистрированного класса. Описание конфигурации и
ограничений протоколов: `sources/modules/lan/readme.md`.

## Инструменты разработчика (этап 6) — архитектура

Решения, обязательные для пунктов 6.2–6.8 (поиск по коду, многофайловые патчи, git, LSP,
запуск проверок, агент-разработчик, разработка WORK изнутри WORK). Контракт — инварианты
11–14 в `rules/threats.md`. Код будет жить в `tools/dev/` (search.js, patch.js, git.js,
checks.js, lsp.js + пул процессов), сборка — в `makeTools`.

### Две арены — третьей нет

| Арена | Что это | Кому | Как работают инструменты |
|---|---|---|---|
| **Дерево WORK (сервер)** | собственный код и данные WORK | поиск и `apply_patch` — любому пользователю (права дерева); git, проверки, LSP — только корневому ADMIN (системная область, как `os_*`: добавляются в `makeTools` лишь ADMIN-сессии, права перепроверяются перед выполнением) | чтение — через ядро с правами пользователя; запись — через ядро (`save_file`): снимок истории, запись отката (`undo.js`), журнал. Файловая система ОС недосягаема — это территория `os_*` |
| **Песочница (компьютер пользователя)** | `/workspace` в контейнере — свои проекты | любой пользователь с доступом к Docker | через `docker exec` (`execRaw`): команда не видит ни хост, ни дерево WORK; истории и отката нет — контейнер одноразовый; в `auto` свободно (risk `'write'`), гарантии — от контейнера (сеть по умолчанию выключена, CapDrop ALL, квоты), а не от подтверждений |

Арена — обязательный параметр инструмента (`where: 'work' | 'sandbox'`): допустимые значения
зависят от сессии (не-ADMIN — только sandbox) и перепроверяются перед выполнением — схема
параметров не единственная проверка. Узлам федерации инструменты разработчика не выдаются.
Субагенту — только по явным маскам в `tools` агента.

### Решения по инструментам

- **grep/glob (6.2)** — `readonly`, `concurrent`. Сервер: обход дерева через ядро (`glob` —
  как `find`, с правами; скрытые `#`-зоны — по правам), содержимое файлов — через ядро; файл
  с внешней пометкой (`server/external-source.js`) или `.eml` в результатах —
  `ctx.entry.untrusted = true` (как `read`). Лимиты: ≤2000 совпадений, ≤200 файлов, ≤256 КБ
  на файл, ≤30 с, вывод ≤30 КБ. Песочница: exec в контейнере (`ripgrep` добавляется в образ),
  вывод — по правилу `sandbox_exec` (интернет включён — `untrusted`).
- **apply_patch (6.3)** — многофайловый патч: создать/изменить/удалить/переименовать, формат
  `*** Begin Patch` (Add/Update/Delete/Move File с контекстными ханками). **Атомарно**: сначала
  все ханки сверяются с текущим содержимым (несовпадение — отказ, ничего не записано), затем
  запись. Сервер: каждый файл — через ядро (история + `entry.undo`); `target(args)` отдаёт все
  файлы патча — защищённая зона хотя бы в одном → подтверждение всего патча (та же `decide()`,
  что у `write`/`edit`); частичный сбой — откат из снятков уже записанных (всё или ничего);
  карточка diff на весь патч. Лимиты: ≤50 файлов, ≤1 МБ на файл, ≤4 МБ текста патча.
  Песочница: запись во временный файл + `mv`, оригиналы хранятся до конца вызова.
- **git (6.4)** — сервер (ADMIN): `spawn` с явными аргументами — без shell; фиксированный cwd
  (корень репозитория); очищенное окружение (`GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_NOSYSTEM=1`,
  без учётных данных); аргументы проверяются (ref — по регулярке, пути — канонические и внутри
  репозитория, `--` против инъекции опций); таймаут ≤120 с, вывод ≤200 КБ. Чтение
  (`status`/`diff`/`log`/`show`/`blame`) — сразу; `git_commit` — подтверждение каждый раз
  (изменение системы; хеш коммита — в запись журнала, аргументы в журнал не пишутся);
  **`push` — `outbound`: всегда подтверждение, без «разрешить всегда», субагенту не выдаётся
  (`SUBAGENT_DENY`)**; команды, переписывающие рабочее дерево (`checkout`, `reset`, `restore`,
  `stash`, `clean`, `rm`), агенту на сервере **запрещены**: они меняют файлы мимо истории и
  `undo` — правка файлов только через `apply_patch`/`write`/`edit`. Песочница: свободно (свой
  проект); `push` фактически возможен лишь при включённом интернете — его включение уже
  подтверждается человеком как действие наружу (`computer_network`).
- **run_checks (6.6; до него — 8.37, fail-open ветки песочницы)** — запуск тестов/линта/сборки.
  Песочница: свободно (risk `'write'`), таймаут ≤600 с, вывод ≤30 КБ (начало+конец) и код
  возврата, интернет включён — `untrusted` (исполняется чужой код). Сервер (ADMIN): запуск кода
  репозитория = эквивалент `shell` → `risk: 'danger'`, подтверждение каждый раз; команда —
  **только из разрешённого списка**: скрипты `package.json` + `#system/dev.json`
  (`checks: {имя: команда}`, ставит ADMIN); таймаут ≤600 с, вывод с потолком, в журнал — имя
  проверки (команда — из конфига, не из модели).
- **LSP (6.5)** — пул языковых серверов (как `mcp-pool`): ключ — (арена, язык), процесс живёт
  между вызовами, простой 5 мин — закрыть, запрос ≤10 с, окружение дочернего процесса очищенное
  (ключи сервера не утекают), диагностика ≤500 записей / ≤30 КБ. Сервер — ADMIN-пул для кода
  WORK; песочница — серверы внутри контейнера (из образа или установленные пользователем).
  Rename/рефакторинг — запись: политика как у `edit`/`apply_patch`.
- **Агент-разработчик (6.7)** — субагент `ai/agents/developer.md`: маски (grep, glob,
  apply_patch, git_*, run_checks, lsp_*, read/write/edit); набор — пересечение с родительским
  (делегирование прав не расширяет); `requires: system | sandbox` скрывает его, когда арена
  недоступна; заражение наследует от родителя.
- **Разработка WORK изнутри WORK (6.8; до него — 8.38, заражение MCP)** — внешний ИИ-клиент
  (через `/mcp`): readonly-инструменты разработчика (grep, glob, чтения git) входят в
  `MCP_TOOLS`; `apply_patch` — с подтверждением elicitation (защищённые зоны — всегда, без
  «разрешить всегда»); те же `decide()`, хуки и заражение, что у встроенного агента; права —
  пользователя токена.

### Почему так

- Запись на сервере = изменение системы: подтверждение, история, журнал, откат — обходов «для
  удобства» нет (инвариант 3 угроз: любой вход идёт через `decide()` и права ядра).
- Песочница одноразовая и изолированная: свобода там дёшева, цена ошибки — потерянный
  контейнер, а не сломанная система.
- Откаты git — единственный способ менять файлы мимо истории и отката, поэтому на сервере они
  у агента изъяты.
- Потолки вывода и пометки `untrusted` — те же правила, что у существующих инструментов (F28,
  `sandbox_exec`, `external-source`): новых исключений не появляется.
